## 核心术语

| 术语 | 定义 |
|------|------|
| **AgentCore** | 产品名，AI Agent 生态平台。不设中文名 |
| **`AgentCore/` 约定目录** | 全局或项目下的**用户可见**约定根夹，装 `规则/` · `记忆/`（进 `<rules>`）。与本地隐藏旁路 `.agentcore/index/`（code_search）正交；与案卷层 `research/`/`debate/` 正交；**勿与**本地盘默认路径 `~/Documents/AgentCore/`（工作区容器）混淆。**不含**独立「知识/」子树（2026-07-24 否决）。✅ 已落地。→ 见 [`Agent记忆与知识系统.md` §5.0](/docs/03-AI核心/Agent记忆与知识系统.md) |

| **项目（Project / Folder）** | 项目**即**工作区——会话分组 + 项目记忆作用域 + 文件工作区三合一（代码符号沿用 `Folder`）。创建时必选位置：本地文件夹（`local_root_id`+`local_subpath`）或云端空间（`folder:<id>` 共享 scope），创建后不可改；local 模式与本地文件夹 1:1（cloud 项目无本地目录）。项目内会话继承项目工作区；会话**出生定终身**（创建时绑定项目或明确无项目，不支持事后移入/继续到另一项目）。裸聊（无项目）走 per 对话 scratch。→ 见 [`双模式工作区.md` §六](/docs/02-架构/双模式工作区.md) |
| **工作区（Workspace）** | 文件可寻址空间（文件 / 快照 / 执行的作用域），`ws_id = folder:<id>`（项目共享）/ `conv:<id>`（裸聊 scratch）/ `shared:<space_id>`（多人共享空间）——**项目 ⊂ 工作区**：每个项目恰有一个共享工作区，但工作区还含裸聊 scratch 与共享空间，故「工作区列表 ≠ 项目列表」。`folder:`/`conv:` 无独立 DB 表，路径由归属推算。展示语「工作区」仅指文件空间（SidePanel「工作区」tab、`/files`）；权限档枚举值 `workspace`（展示名「开工授权」）是另一义，与文件空间无关。→ 见 [`双模式工作区.md` §九](/docs/02-架构/双模式工作区.md) |
| **共享空间（Shared Space）** | 多人云端共享文件空间——与项目（Folder）平行的独立实体，只有「文件」一个面；成员三档（所有者/可编辑/只读），IM 搜人定向邀请 + 接受制，可编辑成员的 Agent 经会话**挂载**直写（仅云执行对话）。UI 定名「共享空间」。**勿与「（项目）共享工作区」混**——后者指单人项目内多会话共用 `folder:<id>`，无多人成员概念。→ 见 [`双模式工作区.md` §十一](/docs/02-架构/双模式工作区.md) |
| **Agent** | 角色定义实体——包含人设、沟通风格、模型选择，是 Skill 的载体。创作者构建的可复用产品单元 |
| **Skill** | Agent 的领域能力——包含工作流指引、约束、输出格式；市场实体，经绑定注入 Prompt。单一来源（无内联） |
| **Tool** | 确定性动作执行器——无推理；内置函数或市场工具经声明式连接器执行。分两个家族：**动作工具**（执行确定性动作、不留可编辑产物，如 file/grep/web/exec）与**创作工具**（产出可持久编辑的产物类型，见下） |
| **创作工具（Creation Tool）** | 面向用户的工具，每个对应一种**产物类型**（思维导图/画布/多维表格/文档）；有"用户编辑器（人）+ Agent 工具（AI）"两副面孔，共编同一份产物。同属"工具"，故 Agent 也能用 |
| **产物（Artifact）** | 创作工具产出的可持久化、可反复编辑结果；进统一文件/产物体系，可被对话 `@` 引用、分享、重开 |
| **AI 选区改写（assist / rewrite）** | 创作工具（文件编辑器）的 AI 原语，做成**无状态文本进/文本出**：服务端**从不读写文件本身**（本地文件在桌面 fs 桥后、云端在工作区 API 后），只收「选区 + 指令 + 前后文（只读）」、调 `LLMProvider` 返回改写后的选区文本，由前端套 `@codemirror/merge` 逐块评审（人接受/拒绝）。`scenario="file.rewrite"` 归因花费，60s 交互超时；当前仅 L1 选区改写。→ 见代码 `agentcore/assist/rewrite.py` / `services/rewrite.ts` |
| **Rule** | 可复用规则——约束 Agent 行为的指令片段，可安装/共享 |
| **Team** | Agent 团队——多个 Agent 的编排组合，有 captain 和 members |
| **AgentVersion** | Agent 版本——包含 system_prompt、model、tools、delegations 的快照 |
| **Fork** | 复制他人 Agent 并独立改进的机制，类似 GitHub Fork |
| **Delegation** | Agent 委派——一个 Agent 将子任务交给另一个 Agent 处理 |
| **Arena** | 竞技场——多个 Agent 围绕同一主题进行多轮对抗/讨论（多轮辩论）。✅ 已落地为**主持人（Moderator）驱动**的逐轮交锋 → 决策简报 + 交锋叙事线双产物（见 [`辩论编排设计.md`](/docs/03-AI核心/辩论编排设计.md)）；底层仍是普通 AGENT DAG、**非独立执行子系统**（独立子系统仍否决）；≠ best-of-N 择优，见下 |
| **Moderator（主持人）** | 辩论的有状态编排角色（主持 + 裁判 + 书记三合一），落成 CEO `debate` 工具内的确定性循环（非 LLM 委派角色）、辩手为 `depth+2` 叶子。逐轮流程（定议题 → 派辩手 → 判交锋 → 收敛出简报）见 [`辩论编排设计.md` §二](/docs/03-AI核心/辩论编排设计.md) |
| **best-of-N 择优** | 高不确定环节并行跑同一任务 N 个候选、择优输出的策略（`RunPolicy.candidates>1`）；执行策略位而非独立节点种类，与 Arena（多轮辩论）两回事 |
| **MCP** | Model Context Protocol（行业 Agent↔Tool 标准） |
| **A2A** | Agent-to-Agent Protocol（行业 Agent↔Agent 通信标准） |
| **ReAct** | Reasoning + Acting 循环，Agent 的推理-执行模式 |
| **SSE** | Server-Sent Events，对话流式输出的传输协议 |
| **Turn** | 交互聚合层——一次用户消息触发的完整 ReAct + 委派过程 |
| **Run** | 执行单元——一次被调度的 Agent 工作（委派的 worker / DAG 节点）；一个 Turn 含一棵 Run 树。生命周期见 `RunPhase`。代码层统一称 Run（旧称 Step 已废弃），用户展示用「任务 / 子任务」 |
| **CostEvent** | 成本事件——记录单次 LLM 调用的 token 用量和 CNY 成本 |
| **Approval** | 工具执行审批——安全门禁，按 tool_call_id 独立等待 |
| **Checkpoint** | 运行时状态快照——回合级落盘（`paused_turns`）+ 进程内挂起帧，供断点续跑与调试 |
| **AgentCard** | Agent 能力声明——capabilities, input/output_modes, endpoint |
| **TaskRequest** | 标准化委派信封——instruction, context, constraints |
| **可发现性（Visibility）** | Agent 的固有属性，三态：`public`（上架）/ `unlisted`（凭 id 可达但不在发现面）/ `private`（仅创作者）。与 `is_featured`（编辑精选）正交 |
| **Sidecar（本地引擎）** | 本地优先的第二运行通道：桌面 spawn `python -m agentcore.sidecar` 跑**同一引擎**，整轮在用户机器上执行、工作区直连本地真实磁盘；区别于「云端引擎经 `WorkspaceChannel` 遥控桌面」。机制（stdio JSON-RPC / §8.6 宿主端口本地化 / 平台 key 不下放）见 [`双模式工作区.md §十`](/docs/02-架构/双模式工作区.md)、代码 `agentcore/sidecar/`；完全离线演进见 远期规划.md §一（详细提案不在公开仓 / 维护者本地） |
| **local-turn（本地回合回写）** | Sidecar 本机无库，渐进写本机 outbox；主进程 Bearer 回写 `POST …/local-turns`（`CloudStore.finalize(mode=local)` 幂等合并）。桌面 UI 本地提示 `synced_pending`（不进跨端契约）。见 [`双模式工作区.md §10.3`](/docs/02-架构/双模式工作区.md)、`outbox-writeback.ts` / `api/routes/conversations/` |
| **证据台账（evidence ledger）** | 结构化来源表——成稿只引台账 **id**，闸与徽章/来源卡同源可溯。辩论场级（`#e`）：检索期注解 id、笔记行尾绑定，**上 wire 仅消费子集**（深读 + 笔记引用 + 底料）；闸基准 = 本方笔记引用集。回合级调研（`#r`）另路径。共享核同一、wire 分通道，**均不占**有帽的 `citations_event`。→ 见 [`辩论编排设计.md` §4-2.3](/docs/03-AI核心/辩论编排设计.md)、[`工具与能力系统.md`](/docs/03-AI核心/工具与能力系统.md) |

| **GraphScene** | 协作图中间表示（`acts→units→members` + edges + bands）；fold 下游、布局/投影上游的单一结构源。→ [前端技术 §9.13](/docs/04-前端/前端技术与架构.md) |
| **finding** | 红队交互单元：刺→回应→复核（thorough +复攻）三拍产物；前端 `FindingThreads` + 严重度/状态徽章，红队无结辩。→ [前端 UX §4.1](/docs/04-前端/前端UX设计.md) |
| **阶段推进卡** | kind=`stage_card`：幕间一步授权（如「按此开辩」）；跨回合 Dock 常驻，进 process 时间线。→ [前端 UX §三](/docs/04-前端/前端UX设计.md) |
| **团队浏览器** | L3：worker `browser_*` 活动卡 + SidePanel 直播帧 + 用户接管痕迹（≠ 工作区 `preview://` 产物预览）。→ [前端技术 §9.12](/docs/04-前端/前端技术与架构.md) |

## 运行时协作术语

> CEO 组团、挂起、续跑等执行层名词的精确定义；与上表 **Delegation**（泛化委派概念）区分。**delegate** 专指 CEO 工具原语。

| 术语 | 定义 |
|------|------|
| **CEO** | 主 Agent——本回合对话 + 按需组团 + 收尾汇报的 captain。**身份层级**：用户是老板，CEO 受雇于用户、替其掌管按需组建的专家 Agent 团队并对其负责；**用户才是最终决策者**——CEO 关键岔路向用户请示、收尾向用户汇报（与「用户检查点」心智「团队请示领导」一致）。**实现 = captain 根 Run**（`react_loop` 即 `CAPTAIN` 根节点；content/reasoning 走气泡级 delta，非 run 级）。→ 见 [`编排器与CEO主Agent.md`](/docs/03-AI核心/编排器与CEO主Agent.md)、[`执行引擎架构设计.md` §8.4](/docs/03-AI核心/执行引擎架构设计.md) |
| **worker** | 被 CEO `delegate` 委派的队员 Run。`depth < MAX_DELEGATION_DEPTH` 的 worker 默认获 `delegate`+`replan`（委派默认开、无 opt-in 开关）；depth=2 sub-worker 为叶子；单 lead 最多 4 个 sub-worker。**硬上限 `depth ≤ 2`**。→ 见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md) |
| **delegate** | CEO 持有的**内置工具原语**——在 ReAct 内调用来下达子任务、`depends_on` 定形 DAG。≠ 上表 **Delegation**（Agent 间委派的一般概念 / `AgentVersion.delegations` 市场字段） |
| **带现场续派（同人接续）** | `delegate.tasks[].continue_from_run_id`——唤回刚干完活的同一队员，带完整 ReAct 现场（transcript）接着干：改自己的稿或接强相关新任务（同一动作，task 内容区分；旧独立工具 `revise` 已退役）。wire `continues_run_id` 恒指现场根；图上挂「续 ×N」接续链节点、状态条「接续 N 次」。现场保留 =「对话在，现场就在」（随删对话级联清理）；miss / 超限明确拒绝回落冷 `delegate`。→ 见 [`多轮编排与同人续派.md`](/docs/03-AI核心/多轮编排与同人续派.md) |
| **captain** | 一次 Team 执行的指挥 Run。CEO 为根 captain；嵌套委派时，`depth < 2` 的 worker 默认即为其子团队的 captain（委派默认开），子成员产出上卷后由该 worker 整合 |
| **Interaction** | 统一挂起原语——引擎停下等客户端回值。进程内 `InteractionRegistry` 收编审批 / 发问 / 本地工具 / 计划评审 / 开工卡 / 升级 / 逐轮辩论等全部 kind，热路单一 resolve 端点 `POST …/interactions/{id}`。kind 清单与统一生命周期权威见 [`执行引擎架构设计.md` §8.2](/docs/03-AI核心/执行引擎架构设计.md)。辩论掌舵**不走**此桥——ambient steer 队列（见 [`辩论编排设计.md §六`](/docs/03-AI核心/辩论编排设计.md)） |
| **orphaned（已失效）** | 交互的第三终态（与 resolved 并列）：登记过但已无人能收答复（服务重启 Future 丢失 / 回合已结束 / 整轮重跑）。journal 事实 `interaction_orphaned`，前端统一灰态「已失效」；**不是**用户拒绝、也不是超时 |
| **plan_review** | Interaction kind + DAG 波间结构化挂起：step 带 `checkpoint_after` 且已完成、下游仍待跑时，`WaveScheduler` 在波间 `await` 用户 continue/adjust/stop（adjust 将备注注入未跑下游 `steer`）。前端 `PlanReviewCard` |
| **ask_user** | Interaction kind + CEO **唯一的「向用户发问」内置工具**——开场引导（开工提案卡）与途中拍板共用一卡一套机制，`blocking`（默认 true）正交决定是否挂起回合；属 `ToolCategory.INTERACTION`，worker 不装配。机制（决策分档 / 开场味·途中味 / 非阻塞对偶 / `note` 拼装）见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)、代码 `tools/builtin/ask_user/` / `CheckpointCard.tsx` |
| **kickoff（开工提案卡）** | **已并入 `ask_user`**（开发期重构，不留兼容层）：开场引导不再是独立工具 / 独立事件，而是 `ask_user` 的「开场味」内容形态。原「开场即终回合、不挂起、用户选择作为下一条消息」的设计已撤销——现统一走挂起 + 恢复，由**运行时**（而非模型）决定「该结束还是该挂起」，模型只决定要不要发问。→ 见 ask_user 词条 |
| **team_preview（开工卡）** | Interaction kind + 编排层**机制门卡**：`delegate` / `debate` fan-out 前由公共 kickoff gate（`runtime/kickoff/`）决定是否挂起，= 计划确认 ∪ 能力授权（原 `delegation_authorization` 已并入），事件对 `team_preview_required` / `team_preview_resolved`。触发是机制强制（受自治三档与跳卡规则管辖），非模型自愿——与 **kickoff（开工提案卡）**（`ask_user` 的开场内容形态，上一词条）是**两张不同的卡**，口语「开工卡」仅指本词条。→ 见 [`编排器与CEO主Agent.md` §五](/docs/03-AI核心/编排器与CEO主Agent.md) |
| **用户检查点** | **产品/UI 层**——会话内用户拍板决策的卡片（`ask_user` 问答卡、`plan_review` 计划评审卡、`ResumePrompt` 续跑卡等）。用户心智 =「团队请示领导」 |
| **Checkpoint**（引擎） | **运行时层**——上表已有词条；此处强调与「用户检查点」区分：引擎内的状态/挂起帧快照（如 `paused_turns` 回合级落盘、`TurnSuspension` 帧），供断连续跑与调试，**不是**用户可见的拍板卡片本身。用户检查点触发后可能伴随引擎 Checkpoint 持久化（2b） |

## 模型术语

> 用户面配「一个模型」，引擎内部跑「场景画像」分化执行参数——两者正交、易混，故并列于此。

| 术语 | 定义 |
|------|------|
| **用户模型（BYOK 配置）** | 用户在「设置·模型配置」自备的 **OpenAI 兼容服务商列表**（每个服务商 = label + `api_key` + `base_url` + 默认模型，可同时配多家；账号级 chat/后台默认各一对 `(provider_id, model)` 指针）。单个 turn 全链路（CEO、worker、辩论辩手）统一注入该 turn 解析出的 model；probe 按服务商产出 `supports_tools` 作 soft gate。**被否决：质量档矩阵**（按角色分选 Flash/Pro）——多数用户只想配一个能用的模型。→ 见 [`编排器与CEO主Agent.md` §2.1](/docs/03-AI核心/编排器与CEO主Agent.md) |
| **场景画像（ModelProfile · profile）** | 每个 LLM 使用场景的内部参数包（model 占位 + 温度 + ReAct 回合预算等）。`chat`（单聊 / CEO 默认回复）、`agent`（统一 worker 执行参数档，回合预算 28）、`memory` / `title`（后台 one-shot）。**内部实现，不外露**；用户 model 经 overlay 统一替换各画像的 `model` 字段，画像仍分化执行参数。→ 见代码 `llm/profiles.py` |
| **思考开关（thinking）** | 思考 / 非思考两态（provider `thinking.type`）。CEO / worker / 单聊思考 on；后台 one-shot（`title` / `memory` / `compaction` / `followups` / `file.rewrite`）对 DeepSeek V4 已发 `thinking.type=disabled`。无 per-agent 思考强度档——worker「力度」差异由委派协作结构（拆分 / 复审 / replan）表达，不再有 `ModelTier{fast,strong}` 或思考强度覆盖（2026-07 整体删除） |

## 命名约定（代码符号 ↔ 展示文案）

统一术语、消除「同义多词」。代码符号（标识符 / 字段 / 事件 key）用规范名，面向用户的中文展示用展示文案；二者不混淆。开发期无兼容层，旧词直接废弃。

### 执行单元：Run（弃用 Step）

- 代码层一律 `run`：`run_id` / `RunPhase`（后端权威生命周期：queued·running·completed·failed·skipped·cancelled·retrying）/ `RunStatus`·`RunNode`（前端投影态）/ `runs`；图节点高亮由 SidePanel 当前激活 run tab 派生（早期 `selectedRunId`/`selectRun` 跨 store 选中态已弃用）。
- 旧的 `step` 词汇（`step_id` / `StepStatus` / `steps` / `stepId` …）全部废弃。
- 用户展示文案仍用「任务 / 子任务」（展示语，非代码符号）。
- 例外：与 Run 无关的通用「step」保留——如 React Flow 的阶梯边 `StepEdge`、CSS 缓动 `step-end`、时间轴步进 `STEP_INTERVAL`。

### 终止：状态 cancelled，动作 stop

- 数据层（状态值 / `FinishReason` / 投影态）= `cancelled`。
- 动作层（按钮 / handler / 动词）= `stop`（如 `stopGeneration`）。
- 中文展示统一「已停止」（用户主动喊停，「停止」比「取消」自然）；弃用「中止」作其 gloss（例外：`AbortController` 机制本身、部署/进程「终止」、DB「已取消」各有所指，保留）。

### 重跑：regenerate（整轮）vs retry（重试）

- `regenerate` = 从某条用户消息整轮重新执行的原语（后端 `/regenerate`、`regenerate_chat`；前端 `runRegenerate`）。两种入口：直接重新生成、改输入后重发。
- `retry` = ① 前端传输错误后重发上一请求（`RetryBanner`）；② 后端自动重试（`RunPhase.RETRYING` / `max_retries`）。
- 中文展示固定三词：**重新生成**（要个新答案）/ **调整后重发**（改了输入）/ **重试**（失败后再试）。弃用游离的「重跑」。
- 例外：「重跑」作通用 rerun 动词保留——CI / 工作流重跑、`alembic` 重跑、`react_loop` 重跑、布局重跑等与「整轮重答」无关的场景。

### 团队角色：队员 / captain / 主 Agent

- **worker 的中文展示 = 队员**：被 `delegate` 委派的 worker Run，中文一律「队员」（计费 role / UI / 文档同）。弃用「组员」；prompt 里指代被委派 worker 的「成员」亦收敛为「队员」。
- **保留「成员」的合法所指**：① Team 结构成员（`captain + 成员`）；② IM 群成员 / 设置页「成员」（人类用户）；③ 嵌套委派的「子成员」。
- **CEO = 主 Agent**（产品名 / 对话者）；**协调者** = CEO 的角色描述（只读边界、产出全委派）；**captain** = 指挥 Run（英文保留、不译；CEO 为根 captain，`depth < 2` 默认带子队的 worker 为子 captain）。弃用「队长」「协调官」作上述任一的 gloss（测试角色串等任意输入不在此列）。

### 模型相关：场景画像 / 思考开关

- **ModelProfile 的中文 = 场景画像**（内部参数包，不外露用户）。弃用「模型档位配置」指代 ModelProfile。
- **已删除**：worker 模型档位（`ModelTier{fast,strong}` / `model_preference`）与 per-agent 思考强度（reasoning effort）。worker 回合预算统一为单一上限，「力度」由委派协作结构表达；节点不再有「用哪档模型」徽章。
- **思考模式**（DeepSeek API `thinking` 开关）保留：仅区分思考 / 非思考，无强度档。

### 对话实体：对话（AI 实体）vs 会话（作用域 / session / IM）

- **AI 对话实体 = 对话**：用户与团队的一通会话单元（`Conversation`）。中文一律「对话」——对话页 / 对话行（`ConversationItem`）/ 对话列表（`对话列表设计`）/ 对话管理页（`/conversations`）/ 新建对话 / 旧对话 / 上次对话。弃用「会话列表 / 旧会话 / 上次会话」作 AI 实体 gloss。
- **保留「会话」的合法所指**：① 作用域限定词（`会话级` vs `turn 级`、当前会话、本会话、跨会话、会话内、每会话、切会话）；② 认证 session（`认证与会话`、Cookie / refresh）；③ IM 域会话（`ChatList` 会话列表 / 静音会话 / 每会话未读，人对人线程）；④ 记忆域 session（会话内工作记忆、~~会话摘要~~）。

### 容器三词：项目（Folder 实体）/ 工作区（文件空间）/ 文件夹（目录）

- **Folder 实体的中文展示 = 项目**：凡指 `folders` 实体（创建 / 删除 / 分组 / 筛选 / 记忆作用域）一律「项目」——新建项目 / 删除项目 / 按项目筛选 / 本项目记忆。弃用「文件夹」「工作区」作该实体 gloss。
- **代码符号一律 `Folder`**（`/v1/folders` / `FolderMeta` / `CreateFolderMenu` / `DeleteFolderDialog`），「项目」只出现在用户可见文案（同 Run ↔「任务」范式）。例外：草稿意向判别值 `draftWorkspaceIntent.kind="project"` 保留。
- **工作区 = 文件可寻址空间**（见核心术语词条）：SidePanel「工作区」tab、`/files` 工作区列表、`ws_id`。不作 Folder 实体 gloss。
- **文件夹 = 文件系统目录**：文件树「新建文件夹」、新建项目「选择已有文件夹」（OS 选目录 = 以该目录创建 local 项目）。
- **权限档 `workspace` 的展示名 = 开工授权**（开工卡一次授权语义；枚举值保留，与文件工作区无关）。
- 例外保留：`project*` 作投影动词（`projectExecution` / `projectFlowGraph`）、pnpm workspace 等 monorepo 工程用语——与产品三概念无关。

### 消息气泡：对话气泡（AI）

- **AI 消息气泡 = 对话气泡**（`MessageBubble`，用户提问 + CEO 流式作答同栈）。弃用「聊天气泡」作其 gloss。
- 保留：IM 域人对人气泡（`ChatBubble`，自身文案区别于「AI 对话气泡」）。

### 审批动词：放行（门）/ 允许（用户按钮）

- **门动作 = 放行**（`ApprovalGate` 放过、检查点 continue、fail-open、CORS、并行批量放行）；**用户按钮 = 允许**（「允许一次 / 本轮内都允许」）；**名词 = 审批**（审批卡 / 审批门 / 审批三态）。弃用「批准」作「放行」的游离同义词。
- 保留不同所指：**授权**（`授权根` / 授权语义「这类操作我信任」）、代码符号 `approve`（`autoApproveSiblings` 等，英文保留）。

### 凭据 vs 凭证（credentials）

- **credentials 的中文 = 凭据**（`LLM 凭据` / BYOK 凭据 / 凭据加密〔安全 §七〕/ 凭据来源）。弃用「凭证」作 credentials gloss。
- 保留不同所指：**凭证式 CORS**（`credentialed` 标准术语，不译「凭据式」）、**防幻觉凭据**（= 证据 / 依据，另一义）。

### 交互不答语义：timed_out（拼写）/ 已失效（orphaned）

- **escalation 结算的超时态 = `timed_out`**（单一拼写）；弃用 `timeout` 作该状态值（`CheckpointDecision.timeout` / debate 决策 `timeout` 是另一语义——「引擎按默认推进」的决策值，保留）。
- **「已失效」= orphaned**（见运行时协作术语表）；弃用「过期 / 作废」作其 gloss。中文展示「已失效（回合已结束或服务已重启）」。

## Agent-Skill-Tool 三层概念模型

### 不可违反的边界

| 维度 | Agent（专家） | Skill（技能） | Tool（工具） |
|------|--------------|--------------|-------------|
| 本质 | 有独立推理的参与者 | Agent 的内在能力（Prompt 注入） | 确定性原子能力 |
| LLM | 有独立画像与系统提示 | 无独立 LLM；知识注入宿主 Agent | 无；由当前 Agent 发起调用 |
| 执行 | 占轮次，参与共享上下文 | Prompt 组装时注入 system prompt | 步骤层内调用，不占轮次 |
| 调度 | 由委派或路由触发 | 绑定后始终注入（超阈值转目录 + 按需取） | Agent 推理决定调用 |
| 前端表现 | 独立气泡/身份标识 | 随「AI 提示词」层公开（工具进阶用法 / 薄技能）+ 运行时「查阅能力」卡；不与工具并列 | 折叠在宿主消息下 |

**核心原则：Agent 与 Tool 概念不相交**——需要 LLM 综合与表达的归入 Agent 轮次；输入输出确定的归入 Tool。不承认「会思考的工具」中间形态。

> **系统 Skill 的归位（能力图鉴）**：当前的系统 Skill（团队编排进阶 / 辩论与交叉审查 / 向用户发问…）本质是「某个内置工具的进阶用法指引」，即 **Prompt 注入**，故在「能力图鉴」里归入 **「AI 提示词」层**（作为"工具进阶用法（薄技能）"一节公开），**不**与「工具」并列成独立目录——能力图鉴只分**工具（确定性代码）+ AI 提示词**两类。拉取它们的 `consult_skill` 是 CEO **编排原语**（`ToolCategory.ORCHESTRATION`），非「技能」类目工具。等真正的**市场域 Skill**（合同审查 / 数据分析等独立于工具的领域能力）出现，再为其立独立技能目录。决策与否决项见 [`前端UX设计.md` §十二](/docs/04-前端/前端UX设计.md)。

### 技能光谱：单工具薄技能 ↔ 多工具域级技能

「技能」不是单一物种，而是一段**光谱**。行业共识（Anthropic Agent Skills 渐进披露、SoK: Agentic Skills）：技能与工具的真正分界**不是「代码 vs 文字」**——技能里也可含脚本、工具也带自然语言描述——而是 **「原子动作」 vs 「按需加载的多步流程知识」**。本项目的「技能」落在这条光谱的两端：

| 维度 | 单工具薄技能（当前 6 个系统 Skill） | 多工具域级技能（市场 Skill，⏳ 未落地） |
|------|--------------------------------|----------------------------------|
| 实质 | 「**某一个**内置工具的进阶用法」——从工具描述里拆出的"怎么用好它" | 独立于任何单个工具的**领域 SOP**（合同审查 / 数据分析等） |
| 与工具关系 | 一对一贴着某工具（delegate / debate / ask_user） | 自带领域知识 + **编排一组工具**完成成果级流程 |
| 形态 | ≈ 加长版工具说明书；纯 Prompt 注入 | Prompt 指引 + 工具绑定（可含脚本） |
| 能力图鉴归类 | 并入「AI 提示词」层、作「工具进阶用法（薄技能）」一节，不与工具并列 | 出现时立**独立技能目录** |

**为何当前这 6 个读起来像工具描述**：它们就在薄端——本质是「单个工具的进阶用法」、为省常驻 prompt 预算才挪成按需 `consult_skill`。等多工具域级技能出现，「自带领域知识 + 编排多工具」一眼就与「某工具的用法」区分开，独立技能目录才名正言顺。

### 判定标准

- 需要 LLM 推理（有 ReAct 循环）→ **Agent**
- 描述一类任务的 SOP 工作流（Prompt 指引 + 工具绑定）→ **Skill**
- 不需要推理、给参数固定执行返回结果 → **Tool**

### Skill 与 Rule 的区分

| 维度 | Skill | Rule |
|------|-------|------|
| 职责 | 「怎么做」— 多步操作模板、领域指引 | 「不能做什么」— 行为约束、质控合规 |
| 粒度 | 域级（如"合同审查"、"数据分析"） | 原子级（如"中文优先"、"禁止虚构") |
| 加载方式 | 绑定加载；超阈值转目录 + consult_skill 按需取 | 按 apply_mode 分流：always 常驻、conditional 按条件注入、on_demand 按需取 |

### Agent→Skill 降级判定

当某个 Agent 满足以下全部条件时，应降级为 Skill：

1. 其**每次判断都依赖领域上下文**（不具备独立完成推理的能力）
2. 领域 Agent 挂载对应 Skill 后**可独立完成同等质量输出**
3. 该 Agent 的存在**增加调度歧义**（委派路由难以区分）
