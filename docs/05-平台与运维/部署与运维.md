## 一、服务器环境

### 域名拓扑（参考自托管）

公开文档用占位域名描述角色；自托管时换成自己的 DNS。品牌官网可另配。

| 角色 | 示例主机名 | 典型路由 | 用途 |
|------|-----------|---------|------|
| API + web 客户端 | `app.example.com` | A/AAAA → 应用机 Nginx | API（`/api`）+ `dist-web` 同源 SPA |
| 手机网页 | `m.example.com` | Pages / 静态托管 | `apps/mobile` SPA；CORS allow-list 须含此 origin |
| 官网 | `www.example.com` | Pages / 静态托管 | `apps/website` |
| 管理后台 | `office.example.com` | 反代或 Tunnel → 本机回环端口 | `apps/admin` SPA；建议再加身份门（如 Access） |
| 可选中转 | `relay.example.com` | Tunnel / 反代 | 仅在启用对应能力时需要 |

生产具体主机名、Tunnel ingress 与机上 Nginx 全量配置**不入仓**；仓库只提供 `deploy/nginx/*.conf` 片段与 compose 蓝图。

> 硬件规格、公网 IP、SSH 密钥路径等运维快照**不入 docs**（随实例漂移）；需要时查运维 runbook 或云控制台。

### 官网（Cloudflare Pages）

营销官网部署在 **Cloudflare Pages**（Next.js 静态导出），与后端解耦、零服务器占用。

| 项目 | 值 |
|------|------|
| 项目名 | `agentcore-website` |
| 源码 | `apps/website`（Next.js 静态导出，`output: "export"`） |
| 构建 | `next build --webpack`（**不可用默认 Turbopack**：Next 16 下 Turbopack 不产出 `out/`，会部署成空站） |
| 部署 | **Cursor Agent 本地脚本** + wrangler direct-upload（✅ `pnpm -C apps/website deploy:pages`） |
| 凭据 | `deploy/.env.deploy.local`（或 `apps/website/.env.deploy.local` 仅 CF token） |

**部署决策**（2026-06）：不再用 GitHub Actions `push` / `workflow_run` 自动部署官网。

| 方案 | 结论 |
|---|---|
| Cloudflare Pages **Git OAuth 集成** | **否决**——现有项目是 direct-upload 类型，改接 Git 须重建项目并迁移 apex 域名 |
| GitHub Actions + wrangler | **否决**——私有仓 Actions 分钟配额易耗尽；配额用尽时 job **0 step 秒失败**，push 后无法可靠上线 |
| Cursor 代部署（本地 build + wrangler） | **采用**——与 direct-upload 模型一致；token 本地一次配置；用户说「部署官网」时 Agent 执行并 curl 验收 |

✅ 已落地（官网 + mobile + admin）：`pnpm -C apps/website|mobile deploy:pages` / `pnpm -C apps/admin deploy:production`、`.cursor/rules/cursor-deploy.mdc`、GHA push 触发已关闭。根 `package.json` **无** `deploy:pages` 脚本。

→ 见代码 `apps/website/package.json`、`apps/website/scripts/deploy.mjs`、`.cursor/rules/cursor-deploy.mdc`

### web 客户端（同源 · 服务器 Nginx）

主力 web 客户端（`apps/desktop` 渲染层跑在浏览器，形态 A：web = 「云工作区」一等入口）**同源**部署在 **app. 根路径**：页面在 `https://app.example.com/`、API 在 `https://app.example.com/api/`，由**同一台 Nginx** 托管 → 第一方 cookie、**零 CORS**。选同源而非另开静态子域的理由：cookie 鉴权同源最稳，且 API 已在该 Nginx 上，加一段 `location /` 即可。

| 项目 | 值 |
|------|------|
| 源码 | `apps/desktop`（Vite 渲染层 webapp 入口 → `dist-web/`） |
| 构建 | `pnpm --filter agentcore-desktop build:webapp`（`.env.production` 指向你的 API 同源 URL） |
| 静态目录 | `/opt/agentcore/web/dist` |
| 部署 | 同步静态产物后 `nginx -t && reload`（**仅同步文件，不改 server 块**） |
| Nginx | 一次性把 `root` + `location /` + `/assets` 合入 app. `:443` 块；**勿动** `/api`、`/storage` 等——参考 `deploy/nginx/app-web.conf` |
| 后端 | 同源 → **无需 CORS** |

→ 见代码 `apps/desktop/scripts/deploy-web.mjs`、`apps/desktop/package.json`、`deploy/nginx/app-web.conf`

### 云端执行灰度（gVisor）

> 执行模型 / 产物写回 / 护栏语义权威见 [安全权限与治理 §五](/docs/05-平台与运维/安全权限与治理.md)；本节只写部署面。灰度策略（已拍板）：先在现有 2C8G 生产机上以并发 / 时长限额灰度，用真实负载定升配。

**开启步骤**（默认关。启动期跑一次沙箱健康探测：失败**不拒启**，打 `sandbox.cloud_health_failed` warning 并整类不装配执行工具（`code_execute`/`test_run`），能力行如实显示未装配——fail-safe 诚实降级，不存在悄悄回落 subprocess 的路径。原「只开 env 不叠 compose 即拒启」已被此取代）：

1. **镜像**：`apps/server/Dockerfile` 已内置 runsc 下载层（官方源 `storage.googleapis.com`；生产机拉不动时 `--build-arg RUNSC_URL=<镜像源>`，无校验文件的镜像源加 `RUNSC_SHA512=skip`；`INSTALL_RUNSC=0` 可跳过）+ 沙箱运行环境（系统 python3 预装 python-pptx / python-docx / openpyxl / pandas / numpy / matplotlib / reportlab / pypdf / pillow，`fonts-noto-cjk` 中文字体，nodejs）。正常 `pnpm deploy:backend <sha>` 构建即含。
2. **配置**：`deploy/config/production.env` 按 `production.env.example`「云端代码执行」段开 `GVISOR_ENABLED=true` 与护栏 `GVISOR_*`（可先用样例默认值）。
3. **编排**：`deploy-server.sh` / `finish-server.sh` 在检测到 `GVISOR_ENABLED=true` 时**自动**叠加 `deploy/docker-compose.sandbox.yml`。活栈目录（`AGENTCORE_DEPLOY_DIR`）若缺该文件，finish 脚本会回退到仓库 `repo/deploy/docker-compose.sandbox.yml`。**宿主前置**（Ubuntu 24.04）：`kernel.unprivileged_userns_clone=1`（或等价 sysctl）；`kernel.apparmor_restrict_unprivileged_userns=0`（24.04 默认 1 会拦 runsc 非特权 userns，须显式放开）。runsc 安装路径固定 **`/usr/local/bin/runsc`**（Dockerfile 下载层），**不可改路径**——宿主 AppArmor profile 按此路径附着。叠加 compose 的 `apparmor=unconfined` 姿态**无需改**。
4. **发布前自检**（开发机 Windows 可跑非 live；真 runsc 须 Linux/Docker）：
   `python apps/server/scripts/verify_gvisor_sandbox.py`；镜像内：
   `python apps/server/scripts/verify_gvisor_sandbox.py --live`（见脚本头注释 Docker 用法）。

**部署后人工验证清单**（开发机 Windows 无法跑 runsc，以下必须在生产/Linux 机上过一遍再放灰度）：

1. 启动即健康：`GVISOR_ENABLED=true` 下 api 正常起；启动日志 **`sandbox.cloud_health_ok` 为 DEBUG 级**（生产 info 级默认看不到，属正常）；**`sandbox.cloud_health_failed` 为 WARNING 级**（生产可见）。故意改坏 `GVISOR_RUNSC_PATH` 仍应正常起，但日志见 `sandbox.cloud_health_failed` warning，且云对话不装配 `code_execute`（能力行显示未装配）。
2. 容器内 runsc 真能跑：云对话让 AI 执行 `print("ok")` 类代码——若报「代码执行环境启动失败」，按叠加层注释排查 seccomp / userns 前置。
3. 产物写回端到端：让 AI 用 python-pptx 生成一份 pptx → 工具结果出现「已写回工作区」→ 工作区面板能下载打开；中文内容不是豆腐块（字体）。

6. 资源观察：灰度期定期 `docker stats` 看 api 容器内存（沙箱并发时应 < 3g）、宿主负载，用真实负载决定升配（§六）。

### 7.1 版本钉定

**多轨道 semver**（开发期）：API（`pyproject.toml`）、Desktop（`package.json` + `desktop-v*` tag）、Web 客户端（mobile/admin build 注入 `__APP_VERSION__` + git SHA）**独立 bump**（`pnpm bump-version <track> patch|minor|major|x.y.z`）；About / 系统页双行展示「客户端版本」与「API 版本」。所有客户端请求带 `X-Client-Platform` + `X-Client-Version`（→ `scripts/client-build-info.mjs`、各端 `lib/clientBuildInfo.ts`）。

部署一律按 **git SHA**，不按浮动 `latest`。应用镜像构建期注入 `GIT_SHA` / `BUILT_AT`，运行时经 `GET /version` 暴露（端点已实装；启动入口在环境未注入时自 git 工作树补 SHA、按启动时刻补构建时间，发布流水线经环境变量注入则优先）。部署脚本传 `latest` 时，会先解析为当前 `master` 的具体 SHA 再 pin——容器跑的永远是确定 SHA（可追溯、可秒回）。

### 7.2 发布点（Release Point）

`master` 是 WIP 快照主干，**HEAD ≠ 可上线点**。用 `prod-*` tag 标记发布点（语义：「这个 SHA 是要上线的版本」）。部署以发布点为准，而非 `origin/master`——tag **仅作标记**、不触发自动部署（`deploy-backend.yml` 仅 `workflow_dispatch` 备用，§三 CI/CD 决策；生产当前尚未走脚本自动化，见 §三落差；漂移哨兵仍 ⏳）。

### 7.3 漂移检测

Admin 系统页 **发布漂移** 卡片（✅）：客户端拉 GitHub Latest（`AgentCore-releases`）与官网 `/api/desktop-release`，对比下载页是否滞后；控制台 SHA vs API SHA 标注「异轨/同部署」。

CI 每日自动比对线上 `/version` 与最新 `prod-*` tag（⏳ 目标；MVP 未接入）：

- prod 落后 tag → 「发了版没部署」（真漂移，告警）
- `master` 超前 tag → 「攒了未发布的 WIP」（正常，不告警）

桌面端同理：比对 `package.json` version 与公开发布仓的 `releases/latest` tag（⏳ 未接入）。

### 7.4 Deploy ≠ Release

构建/部署之上还有一层「部署 ≠ 发布」解耦——后端功能可先暗发到生产，由配置/特性开关翻开才对用户可见。支持灰度 + 最低客户端版本门控（让后端先于桌面发版，仅追上的客户端点亮）。

#### 跨轨道发布协同（2026-06 决策）

**不强制**后端与桌面（或各客户端）同一天、同 SHA 锁步发布——§7.1 多轨道 semver 的设计意图即**独立节奏 + 按需协同**。`prod-*` 与 `desktop-v*` **不绑定**；Admin 漂移卡片标注「异轨/同部署」是观测，不是告警。

| 变更类型 | 是否要快跟 | 说明 |
|---------|-----------|------|
| 纯后端（客户端无感） | 否 | skills / evals / prompt 等；桌面不必跟 |
| **协议 / 事件契约** | **是（天级窗口）** | 动了 `packages/contract-types`、protocol-conformance 向量、各端 fold → 后端 + mobile/admin **同日** deploy；桌面 **7 天内** patch 发版 |
| 纯客户端 UI | 否 | 主题 / 布局；后端不必跟 |

**判据**：本次 PR 是否改协议 fold 或事件类型？是 → 走「协议变更」行；否 → 各轨道独立发。

**协议变更轻量流程**（人工 checklist，非自动化门禁）：

1. `pnpm conformance` 全绿后再 prod deploy
2. 同日：`prod-*` + mobile/admin Pages deploy
3. **7 日内**：`desktop-v<patch>` + 官网 `FALLBACK_VERSION` + `deploy:pages`
4. 旧桌面用户：对话通常仍可用（后端向后兼容发事件），新 UI 等 auto-update；不应依赖「必须同天发桌面」来保活

**否决**：`prod-vN` 与 `desktop-vX.Y.Z` 强制同 tag / 同 SHA 发布——发布成本与回滚独立性不划算。

⏳ 远期：`min_client_version` 特性开关接线后，协议变更类功能可后端先上、仅新版本客户端点亮（§7.9），进一步降低人工记「7 天内补桌面」的负担。

### 7.5 Monorepo 选择性构建

`push master` **不自动构建/部署**（2026-06 切 Cursor 本地，§三）。Agent 执行 `pnpm deploy:backend <sha>` 在生产机构建 api 推 ACR。⏳ 多服务 retag 优化未纳入。

### 7.6 桌面端构建与双仓发布

| 环节 | 机制 |
|---|---|
| 构建触发 | Win = 本地；Mac = Actions **workflow_dispatch**（仅 `mac`）。`desktop-v<ver>` tag 仅标记，不触发 |

### 7.7 备份与恢复策略

**只备不可重建的主数据**——PostgreSQL + 对象存储（工作区文件）。Redis 是缓存丢了自愈。

| 原则 | 说明 |
|---|---|
| 迁移前快照 | 每次 `alembic upgrade` 前自动 `pg_dump`，失败即终止迁移 |
| 破坏性干净恢复 | 回灌前 `DROP SCHEMA public CASCADE`（非空库直接灌会主键冲突） |
| 停应用再恢复 | 避免并发写入；恢复后不自动起应用（需重新 deploy 对齐版本） |
| 异地副本 | 默认只有本地——防不了整机损坏，放量前必须开异地 |
| **灾备演练** | 备份未验证过恢复 = 没有备份。放量前必做一次完整恢复演练 |

**脚本已入仓** → 见 `deploy/scripts/backup.sh`（全量备份 + 轮转）/ `restore.sh`（破坏性干净恢复：完整性校验 → 确认门 → 停 api → 回灌 → 不自动起）/ `deploy/systemd/agentcore-backup.*`（每日定时 oneshot）。**当前仅覆盖 PostgreSQL**（DATA_DIR 文件 / 对象存储需另行文件级备份）；异地副本与灾备演练仍为运维动作（参数/排程见脚本与 runbook）。

### 7.9 特性开关架构（⏳ 目标设计 · 未实装）

特性开关是 §7.4「Deploy ≠ Release」的落地机制——后端代码先暗发到生产，由配置翻开才对用户可见。**实现现状**：本节为已确认目标设计，服务端三门求值 / 灰度分桶 / `min_client_version` 接线均 ⏳ 未建（现仅有 `desktop_updates_enabled` 熔断与 `config/features.py` 编译期垂直开关；`api/routes/system.py` 注释预留接缝）。

**服务端求值**：灰度/版本逻辑只在后端运行，客户端与后端代码路径都只读「已解析的布尔」。理由：求值逻辑不泄漏到端、各调用方判定一致、单一真相源。

**三道门顺序求值**：每个 flag 按以下顺序判定，任一道关闭即最终为 `false`：

| 门 | 含义 |
|---|---|
| `enabled` | 总开关（关 = 永远关） |
| `min_client_version` | 仅 ≥ 该版本的客户端可见（跨列车安全阀） |
| `rollout` | 灰度百分比（0–100），按稳定 key 分桶 |

**跨列车安全阀**：`min_client_version` 让需要新客户端支持的后端功能先进生产，仅追上版本的客户端点亮——将「后端先上、桌面后放量」的跨列车顺序约束变成开关里的硬门，而非靠人工记顺序。

**分桶策略**：优先用户 `user_id`（同一用户跨设备判定一致），未登录回落到设备 `client_id`（UUID 持久化）。同一 key 永远落同一桶（不抖动），按 flag 加盐避免不同 flag 命中同一批人。登录成功后需重拉开关以纠正分桶 key 切换。

**fail-safe vs fail-open 对偶**——刻意相反的失败行为：

| 机制 | 失败兜底 | 为什么 |
|---|---|---|
| 特性开关 | **fail-safe（默认关）** | 未发布的功能要保守，不能因后端抖动误开半成品 |
| 桌面自动更新 | **fail-open（默认开）** | 已发布的安全网络要保活，可远程熔断 |

**演进预留**：v1 配置驱动（翻转需重启），运行时即时翻转（Redis/DB override）为 v2 注入缝。

## 八、配置分层与种子数据 ✅ 已确定

### 8.1 启动依赖层级

| 层级 | 服务/配置 | 失败行为 |
|---|---|---|
| L0 硬依赖 | PostgreSQL, Redis | 启动失败 |
| L0 生产硬约束 | `JWT_SECRET_KEY`(非默认/非空)；`billing_mode=byok` ⇒ `ENCRYPTION_KEY`(64 hex，非空且合法)；`COOKIE_SAMESITE=none` ⇒ `COOKIE_SECURE=true`（桌面端 `app://` 跨站 cookie 前提） | `RuntimeError`（fail-closed，启动即拒） |
| L1 软依赖 | NATS, MinIO, 搜索引擎, 云沙箱健康探测（runsc / subprocess） | 警告后继续，相关功能降级（沙箱不健康 → 执行类工具整类不装配） |
| L2 运行时 | LLM_API_KEY, Embedding | API 可运行，调用时失败或跳过 |

**设计原则**：关键安全配置走 fail-closed（缺失即拒绝启动），功能性配置走 fail-safe（降级但不崩溃）。

### 8.2 环境变量分层

两个 `.env` 文件明确分工：

| 文件 | 内容 | 消费方 |
|---|---|---|
| 根 `.env` | 镜像仓库凭据、镜像标签、依赖密码、内存调优 | compose `--env-file` + 部署脚本 |
| `config/.env` | 应用运行配置（JWT/`ENCRYPTION_KEY`/LLM Key/CORS 等） | api 容器 `env_file` |

DB/Redis/NATS 等连接串在 `config/.env` 仅占位，由 compose 的 `environment` 覆盖为服务名。

### 8.3 种子数据与确定性 UUID

使用 **UUID v5** 确定性生成种子实体 ID：`uuid5(NAMESPACE, slug)` → 同一 slug 永远同一 ID → seed 脚本幂等安全。→ 见 seed 脚本。

### 8.4 种子安全开关

| 开关 | 默认 | 理由 |
|---|---|---|
| `SEED_CLEANUP` | **关** | 破坏性。自动部署若带它，回退到旧 SHA 会跑旧种子集、连带删掉新 SHA 才加的实体——回退应只回退代码、不静默删数据 |
| `SEED_DEMO` | 跟随 dev/prod | 演示数据不应进生产；本地保留以便联调 |

### 8.5 平台 LLM 上游

平台推理（免费档 / `billing_mode=platform`）走 `PLATFORM_*` 三项直连 OpenAI 兼容上游（现状免费档 = DeepSeek 官方 `deepseek-v4-flash`）——架构与凭据以 [`平台LLM接入.md`](/docs/05-平台与运维/平台LLM接入.md) 为权威。部署视角只补两点：

- **改 `PLATFORM_MODEL` / `PLATFORM_BASE_URL` / `PLATFORM_API_KEY` 须重启后端**（本地重起进程；生产 `finish-server.sh` 或 compose 重拉 api）；`PLATFORM_BASE_URL` 若走带版本前缀的兼容端点须含正确后缀（DeepSeek 官方为根 URL，无强制 `/v1`）。
- **验收信号**：模型 id 会在四处同时可见——聊天输入区模型徽章、`GET /v1/llm/key/status`、SSE `run_completed.model`、计费 `cost_events.model`；sidecar 回合另确认 `inferenceToken.ts` 的 `baseUrl` 命中 `/v1/inference/v1` 代理。上游不可用的排查步骤（curl 直连 / 日志关键字）→ 同上权威文档。

## 九、工程门禁与结构治理 ✅ 已确定

> 用 CI 不变量替代人工纪律，防止多 Agent 并行开发下行为回归/类型债/结构腐化悄悄累积。

### 核心哲学：棘轮（Ratchet）

基线 = 当前现状，落地当天全绿，只拦新增腐化。修好真问题就收紧基线（只降不升），放宽必须在 PR diff 里显形并给理由。

### 三道门禁

| 层 | 拦什么 | 策略 |
|---|---|---|
| **行为回归** | 后端 lint + 测试，前端类型检查 | 合并前 CI 硬阻塞 |
| **类型债** | tsc strict / mypy strict | 棘轮：逐文件计数基线，不允许新增错误。棘轮终局 = 修到零 → 升为硬门禁 |
| **结构治理** | god-file 膨胀、模块漏文档 | 行数棘轮（超标存量登记天花板）+ 模块文档守卫 + 清单守卫 |

### 跨端契约门禁

> **实现现状**：✅ 已写入 `ci.yml` 的 `contracts` job（"Contracts + conformance (gen + drift gate)"）：`node scripts/gen-types.mjs`（重生成 REST + SSE 契约产物）+ `agentcore.conformance.export`（重生成一致性夹具）+ `git diff --exit-code`——committed 产物与真相源漂移即红。**但 GHA 无配额、CI 实际不跑 → 发布前本地手动跑这三步核对 0 diff。**

后端改 schema / SSE 事件必须重新生成前端类型并提交，`git diff --exit-code` 拦截 generated 静默漂移（目标）。覆盖两条契约：

| 契约 | 真相源 | 生成产物 |
|---|---|---|
| REST | OpenAPI schema | `openapi.ts` |
| SSE | 后端 EventType + payload dataclass | `sse-events.ts` |

`task gen:types` 一次重生成两者。根除「后端发了新事件/字段、前端 union 或 interface 漏抄、功能静默装死」。

### 拆分实操经验

- **facade + 子包**：按子域拆，`__init__` 全量 re-export 保持公共 API 不变 → 调用方零改动
- **mixin vs 协作者类**：跨切面、读写宿主多字段的状态逻辑用 mixin——经 MRO 保留 `self._x()` 调用、零调用点改动
- **棘轮行数口径**：脚本内自产自校，CI 与基线自洽；勿用不同工具对账（口径不同）
- **陷阱**：移动挂着门禁的文件要同步硬编码路径，否则门禁静默失效

## Cursor 代部署操作手册

> **逐步命令 / 铁律速查** → `.cursor/rules/cursor-deploy.mdc`（与下文决策互补，docs 不重复抄命令表）。

**2026-06 决策**：部署/发版不走 GHA push 触发；GHA 仅 `workflow_dispatch` 备用。凭据 `deploy/.env.deploy.local` 不入仓、chat 不回显。主路径 = `pnpm deploy:backend <sha>`（§三）；Pages 脚本在各 app 内（`pnpm -C apps/website|mobile deploy:pages`），根包无 `deploy:pages`。

### 决策与落差（代码看不出来）

| 主题 | 现状 / 决策 |
|---|---|
| 版本漂移门禁 | 前端 deploy 构建前 `assertBackendContractSatisfied`：HEAD 须为线上后端 sha 的祖先；新增/改接口必须先发后端。强发 `--force` / `DEPLOY_SKIP_CONTRACT_GATE=1` |
| 后端构建拓扑 | 生产机 `git checkout` → `docker buildx` → ACR(VPC) → `finish-server.sh`；日常勿在本地 Windows 打生产镜像 |
| 桌面发版分工 | Win = 本地 `release:win`；Mac = GHA 仅 mac；**勿用 GHA 打 Win**；draft 汇入 `Lawofall/AgentCore-releases` 再 Publish（勿 `--publish always` 竞态，见 §7.6） |
| 桌面 bump → 官网 | 须先 Publish 桌面 release，再部署官网（否则 `FALLBACK_VERSION` / latest 会 bake 旧版） |
| web 客户端 | `deploy:web` 只同步静态 + reload，不改 Nginx server 块（一次性接线见 §二） |
| CI | `ci.yml` 触发保留但 GHA 无配额实际不跑；发布前 `pnpm release:gate`（含 schema gate） |
| Schema 门禁 | 本地 offline + 部署 live（停 api → migrate → `alembic check` → 起 api）；见 §三 CI/CD |
| 生产落差 | 脚本链代码就位但尚未接管活栈——见 §三「现状落差」 |

### 验收锚点

| 目标 | 检查 |
|------|------|
| API | `GET https://app.example.com/api/version` → `git_sha` |
| web / 官网 / 手机 / admin | HTTP 200（URL 见 §二） |
| 官网桌面版 | 官网 release 元数据接口（若启用）→ `version` 与 Latest 一致 |

跨轨道跟发范围 → §7.4；门禁 `pnpm conformance`。
