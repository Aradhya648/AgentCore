## 一、设计基线

| 维度 | 选择 | 理由 |
|---|---|---|
| 登录标识 | **用户名 + 密码** | `username` 唯一非空；`email` 可空且唯一，用户可在账户设置自填，留作后期找回/OAuth |
| 令牌传输 | **httpOnly Cookie** | 前端 `credentials:include`、CORS `allow_credentials=True`；SSE/fetch 天然带 Cookie，前端 JS 拿不到令牌明文（抗 XSS） |
| 令牌载体 | **双 Cookie**：access（短）+ refresh（长，path 限 `/v1/auth`） | refresh 限定 path，减小暴露面 |
| 密码哈希 | **argon2id**（`pwdlib[argon2]`） | 规避 passlib+bcrypt≥4.1 兼容坑；salt + 参数内嵌于哈希串 |
| 注册开放性 | **开放注册**（用户名 + 密码）；`REGISTRATION_OPEN` 环境开关可关闸 | 减冷启动；滥用靠 IP 限流 + admin 停用，紧急关闸不回退邀请码 |
| 暴力破解 | 失败计数 + 5 次锁定 15min | |

> **被否**：邀请码门控注册——公网找码摩擦大、空库冷启动依赖预置码；限流 + 关闸 + 事后停用足够。免费额度开放后注册即有平台代付敞口（¥1/月/号，白嫖价值低于刷号维护成本；限额组与总敞口见 [成本配额与计费 §〇·五](/docs/05-平台与运维/成本配额与计费.md)），验证码 / 邮箱验证维持「有滥用信号再加」（信号 = 注册量突增或平台账单异常），首版不加。

> **Schema 真相源**：本仓 ORM + alembic 是数据库 schema 的**单一真相源**。→ 见代码 `db/models/`、迁移目录。

## 二、数据模型

四张表（→ 见代码 `db/models/auth.py`、`users.py`）：

| 表 | 说明 |
|---|---|
| `users` | 账号主体；`role∈{user,admin}`、`status∈{active,disabled}`；`avatar_key` 头像对象键（可空，→ §四 头像）；自助注销置 `deleted_at` 并匿名化（`username`→`deleted_<id>`、`email` 清空、`avatar_key` 置空）+ `status=disabled`（终态，区别于 admin 可恢复停用） |
| `credentials` | 密码与锁定状态，与账号资料 1:1 解耦 |
| `invites` | **遗留表**（注册不再消费）；历史码与 admin 签发 API 可保留但已 deprecated，不删迁移 |
| `refresh_tokens` | 轮换 + 重用检测的载体；**库里只存哈希** |

设计约束：

- **密码只存哈希**：argon2id，不可逆，无明文列。
- **refresh 只存哈希**：明文（`secrets.token_urlsafe(48)` 高熵随机串）发给客户端，库存 SHA-256 摘要——高熵随机串无需慢 KDF，热路径用快摘要即可。
- 遵循数据建模约定（无 ForeignKey、UUID 主键、`server_default`），见 [`../02-架构/核心接口定义.md` §6.2](/docs/02-架构/核心接口定义.md)。

## 三、令牌模型

| 令牌 | 形态 | 生命周期 | 用途 |
|---|---|---|---|
| access | **无状态 JWT**（HS256，claims `sub`/`type`/`session`/`fam`/`iat`/`exp`） | 默认 30min | 所有 API 请求，随 access Cookie 自动携带；`fam`=token_family（旧 token 无此 claim 仍可验） |
| refresh | **不透明随机串**（库存哈希） | 默认 30d（滑动）+ 族绝对上限 | 仅换新 access；随 refresh Cookie 带到 `/v1/auth` |

**族绝对上限**：`refresh_family_max_days`（默认 90）从 `family_started_at` 起算，超限 refresh → 401（与过期同路径清 Cookie）。admin audience（`client_aud=admin`）改用 `admin_refresh_family_max_hours`（默认 24）覆盖。滑动续期不变，封顶优先。

**会话元数据**（`refresh_tokens`）：`client_platform` / `user_agent` / `ip` / `last_used_at` / `family_started_at`；login 写入，refresh 传承 platform 与 family_started_at。终态行（已轮换/已吊销/已过期）经周期 GC（`refresh_token_retention_days` 默认 7，复用 paused-turn 同款 sweep loop）硬删——活跃 tip 绝不删。

access 校验是纯本地 JWT 解码（无需查库）；任何无效/篡改/过期/类型不符一律抛 `AuthenticationError` → 401，调用方统一翻译。

## 四、端点契约

`POST /v1/auth/{register,login,refresh,logout,change-password}` + `GET/PATCH/DELETE /v1/auth/me` + 会话管理 `GET/DELETE /v1/auth/sessions*`；头像在 `/v1/users`（见下「头像」）。响应模型与字段 → 见代码 `api/schemas/auth.py`。

| 端点 | 失败（决策语义） |
|---|---|
| `register` | 403 注册已关闭（`REGISTRATION_OPEN=false`）；422 用户名占用、弱密码 |
| `login` | 401 用户名或密码错误（**不区分账号是否存在**）、账号锁定 |
| `refresh` | 401 缺失/无效/过期/重用/族绝对上限（并清 Cookie） |
| `me`（GET） | 401 未认证 |
| `GET /sessions` | 401 未认证；按 family 聚合活跃会话，`current` 对照 access JWT `fam` claim |
| `DELETE /sessions/{family_id}` | 401；非属主 → **404**（不泄露）；吊销当前会话=登出自己，允许 |
| `POST /sessions/revoke-others` | 401；无 `fam` 的旧 access → **422**（无法识别「当前」；不选 revoke-all，避免误踢自己） |
| `change-password` | 401 当前密码错；422 新密码弱（<8）/与原相同 |
| `me`（PATCH，改资料） | 422 显示名为空 / 邮箱被占用 |
| `me`（DELETE，注销） | 401 密码错 |
| `POST /v1/users/me/avatar`（上传） | 401 未认证；422 非图片/超 `avatar_upload_max_bytes` |
| `DELETE /v1/users/me/avatar`（移除） | 401 未认证（无头像时幂等 200） |
| `GET /v1/users/{id}/avatar`（取图） | **公开无鉴权**；404 无头像/对象缺失 |

**账户自助（账户设置页，均需 `AuthUser`）**：
- `change-password`：验当前密码 → 改新哈希 → **吊销账户全部 refresh family**（其余设备强制重登），并为当前会话**重发新 Cookie**保持登录（异于 admin 重置：当前设备不掉线）。
- `PATCH /me`：改显示名 / 邮箱（PATCH 语义，仅传的字段变；`email:null`/空清空，唯一冲突 → 422）。
- `DELETE /me`：验密码 → 软删 + 匿名化账户（见 §二）→ 吊销全部 refresh + 清 Cookie。**跨域清理在路由层**（auth service 不越界持有他域 repo）：级联软删该用户全部会话（工作区交由保留清扫回收）、撤销其全部对话分享链接（公开面立即 404，见 [安全治理 §一](/docs/05-平台与运维/安全权限与治理.md)）、删其 BYOK key、删头像对象。成本账本（不变量①，append-only）刻意保留。

**头像（个人资料的一部分，→ 见代码 `api/routes/users.py`、`avatars.py`、`storage/assets.py`）**：
- **独立的 `AssetStorage`**（区别于快照的 `StorageProvider`）：头像是「单个每渲染必取的小对象」，非版本化工作区归档；同样两实现（dev 文件系统 / 生产 S3）共用快照那套 S3 配置。
- **内容寻址键** `avatars/<user_id>/<hash>.webp`：键由处理后字节的 SHA-256 决定，故 `UserResponse.avatar_url` 带 `?v=<hash>` 缓存破坏——图变 URL 才变，`<img>` 缓存可设永久；旧对象在换图时尽力 GC。
- **上传读原始字节**（非 multipart）：Pillow 重编码为 256px 方形 WebP（校验真为图片 + 脱 EXIF + 归一格式/尺寸 + 居中裁剪），非图片/超限 → 422。
- **取图端点公开**：头像非密且本就展示给同事（IM/名册），而 `<img src>` 跨域不带 Cookie，故 `GET /v1/users/{id}/avatar` 无鉴权；上传/删除自限（`AuthUser`）。`avatar_url` 是相对路径（后端不感知公网源，前端拼 API base）。

**注册关闸**：`REGISTRATION_OPEN`（默认 `true`，见 `config/auth.py`）。关闸后 `POST /v1/auth/register` → 403；登录与已有会话不受影响。首个 admin 仍可用 `scripts/create_admin.py` 引导（空库无账号时）。

**邀请签发（admin 专属，deprecated）**：`POST/GET /v1/auth/invites`、`POST /v1/auth/invites/{id}/revoke` 仍可调用，但注册路径不再校验邀请码；Admin 控制台邀请码入口已下线。

**用户管理（admin）**：含 `POST /v1/admin/users/{id}/reset-password`——生成一次性临时密码、改哈希并**吊销该用户全部 refresh（强制登出所有设备）**，临时密码仅在响应体返回一次。详见 [`管理员后台.md` §四](/docs/05-平台与运维/管理员后台.md)。

**Bearer-token（手机 / 非常规 origin）✅**：`POST /v1/auth/token`（登录）、`/v1/auth/token/refresh`、 `/v1/auth/token/revoke`——响应体返回 access + refresh 明文，**不设 Cookie**；后续 API / SSE 带 `Authorization: Bearer <access>`。轮换 + 重用检测语义同 §五（宽限窗口 + 前端单飞刷新，手机 `api/client.ts`）。桌面生产仍走 Cookie（`app://`）；手机 web（`m.*`）与 Capacitor（`capacitor://`）走 Bearer。→ 见代码 `api/routes/auth.py`、`tests/integration/test_auth_api.py`（bearer 用例）。

> **注入约定**：`AuthUser`（401）/ `OptionalUser` / `AdminUser`（403）。权限在 **service 层**校验。

## 五、刷新令牌轮换 + 重用检测

refresh 单次使用，every refresh 把旧令牌标 `rotated_at`，并在**同一 `token_family`** 内签发后继（仅 login 起新 family）：

| 场景 | 行为 |
|---|---|
| 令牌首次交换 | 标记 `rotated_at`、同 family 签发后继 |
| 已 `rotated` 令牌在**宽限窗口**（`_REFRESH_REUSE_GRACE`，默认 10s）内再现 | 判为善意并发 → 同 family 补发后继，**不撤销**（不掉登录） |
| 已 `rotated`（超窗）/ 已 `revoked` 的令牌再现 | 判为泄露/重放 → **吊销整个 family**（`revoke_family`），强制重登 |
| 令牌已过期 | 拒绝 |

> **并发宽限窗口（✅ 已落地）**：客户端常一次并发多请求；access 过期时各请求各自 401、各带**同一旧 refresh cookie** 去刷新，若「已轮换即连根撤销」会无故互踢掉登录。故已轮换令牌在 `_REFRESH_REUSE_GRACE`（默认 10s）内再现按同一逻辑刷新、在原 family 内补发后继且不撤销；**超窗**再现才判泄露、连根撤销。前端配套**单飞刷新**（桌面 `services/api.ts` `tryRefresh`、手机 `api/client.ts` `refreshTokens` 各自把并发刷新合并为一次往返，各刷新调用点共用），二者叠加根治「读久了再操作即掉登录」——后端窗口是跨窗口/跨进程/多端的兜底。**桌面本地回合上线后**，Electron 主进程回写器另有独立 `refreshInFlight` 单飞，与 renderer `tryRefresh` **跨进程协调**（只让一方刷新、另一方复用），避免主进程与 renderer 同 family 互踢（见 §七 主进程 Bearer 客户端）。

> **刷新失败三态（✅ 已落地）**：静默刷新的结果分 `renewed / auth_dead / transient`（桌面 renderer `tryRefresh` 与主进程 `refreshAccessToken` 共用该契约，IPC `authRefresh` 同型；手机 `refreshTokens` 同语义）。**仅当刷新端点明确回 401/403**（吊销/过期/重用）才判 `auth_dead` → 跳登录；网络错 / 超时 / 5xx / 429 / 后端重启窗口一律 `transient` → **绝不跳登录**——REST 走服务不可用门（`/readyz` 确认 + 重试页），SSE / realtime 走各自重连，冷启动 bootstrap 走 unavailable 分支；手机端仅 `auth_dead` 才清本地 token 对。**决策理由**：早期「一切失败 = false = 踢登录」把 dev 热重载窗口 / 网络闪断误判为会话失效，refresh 明明有效却被送回登录页（生产部署重启同理）。
>
> **AuthGate 三态门（桌面，✅）**：`loading` / `unavailable` / `unauthenticated`（过门才渲染业务树）。决策：`transient` 刷新失败 → `unavailable`（**不踢登录**）；会话中非 auth 调用的 5xx/网络错须经 `/readyz` 复核后才切 `unavailable`（防单点 500 误杀整屏）。壳与重试页细节 → [`前端技术与架构.md`](/docs/04-前端/前端技术与架构.md) / `AuthGate.tsx`，本文不展开。

## 六、静默刷新与流式通道约束

> ✅ 前端已接 401→刷新→重放链（含 SSE 流式通道）。以下为静默刷新**必须遵守的约束**。

access 过期由 401 触发刷新 → 换新 → 重试原请求，对用户无感；refresh 过期才真正跳登录。重发安全：401 在认证依赖层抛出、handler 未执行、请求无副作用，可安全重发。

**关键约束——流式通道必须各自接入刷新**：聊天 SSE（发消息、恢复、异步委派流）通常绕过统一 HTTP 封装直接 `fetch`。这些通道**必须各自包一层 401→刷新→重发**，否则「读了半小时再发消息」会因 access 过期直接掉登录，而非无感续期。**新增任何绕过统一请求层的 fetch/XHR 通道时，都须接入此机制。**

## 七、Cookie、CSRF 与易踩坑

- **refresh Cookie path（前缀随反代可配）**：refresh cookie 的 path 限定到 auth 端点（不让长期令牌随每个请求外发）。**生产 API 经 Nginx 反代挂在 `/api/` 下**（`app.fashitianxia.xyz/api` → `:8000`），浏览器实际请求 `/api/v1/auth/refresh`，按 RFC 6265 需 cookie path 为其前缀——故 path 必须带 `/api`，否则 cookie 永不回传、access 一过期即掉登录（dev 同源无前缀、测不出此坑）。由 `COOKIE_PATH_PREFIX`（生产 `/api`、dev 空）拼前缀生成，见 `routes/auth.py` `_refresh_cookie_path` + `config/`。**改部署拓扑（反代前缀）时务必同步此值**，与 Nginx location 前缀一致。
- **CSRF**：dev 默认 `lax`（renderer 与 API 同站）；**生产桌面端 `app://agentcore` 与 API 跨站，cookie 强制 `SameSite=None`**——即 SameSite 在生产**不提供 CSRF 防护**（None = 跨站照发）。桌面端 CSRF 安全靠 **`app://` 隔离**：只加载自有打包页、外链走系统浏览器（`setWindowOpenHandler`→`shell.openExternal`）、登录态不内嵌三方网页，故无可被 CSRF 利用的浏览器上下文。**X-CSRF 双提交已落地**（`csrf_enabled` 默认开、对 cookie 会话强制，见下条）——桌面 cookie 会话同受保护，`app://` 隔离为额外纵深；跨站拓扑下**无法靠收紧 SameSite 兜底**（收紧到 lax/strict 即不再跨站发送 → 断鉴权）。
- **CSRF 令牌为无状态 HMAC 签名（实现现状，勿回退服务端存储）**：cookie 客户端的 mutating 请求当前**已**强制校验 `X-CSRF-Token`（`csrf_enabled` 默认开，见 `middleware/csrf.py`），登录/刷新经 `X-CSRF-Token` 响应头下发、前端回显。该令牌**不落服务端存储**：由 JWT 密钥派生子密钥对 `user_id` 签名、按请求验签（`security/csrf.py` `sign_csrf_token`/`verify_csrf_token`，格式 `v1.<nonce>.<exp>.<sig>`），与无状态 JWT access cookie 同构。**这是刻意设计**——早期的「服务端内存同步器令牌」会在后端重启/热重载/多 worker 时被清空，而 JWT cookie 仍有效，导致仍登录的客户端凭旧令牌被打成 `403 CSRF_FAILED`（dev 下 uvicorn `--reload` 每次存盘即触发）。**勿改回服务端存储的同步器令牌**。
- **主进程 outbox 回写 = 一等 Bearer 客户端（✅）**：Electron 主进程可靠回写本地回合 `POST .../local-turns`（[双模式 §10.3](/docs/02-架构/双模式工作区.md)）**不复用** renderer 的 cookie + CSRF 链路——它读 `access_token` cookie 走**纯 Bearer**、请求 `credentials: "omit"`（**不带**会话 cookie 头）。CSRF 中间件仅在「有 Bearer 且**无** access_token cookie」时豁免（`middleware/csrf.py`），故主进程请求**必须不带** cookie，否则仍被判为 cookie 会话要 CSRF。401 用 `refresh_token` 调 `POST /v1/auth/token/refresh`（body 版）续期；归属校验复用 `_require_owned_conversation`（§八），无 IDOR。token 过期 / 登出时 outbox 积压不丢、待重新鉴权续传。→ 见代码 `apps/desktop/src/main/auth-client.ts`。
- **主进程刷新后写回 cookie 的两条铁律**（renderer 的 `tryRefresh` 检测到 `outboxApi.authRefresh` 即**全量委派**主进程，写回错了 = 全端静默刷新失效）：① **SameSite/Secure 按 API URL 推导**——https → `None`+`Secure`（生产跨站）、http（dev localhost）→ `Lax`+非 Secure；不能硬编码 `None`，Chromium 规则「SameSite=None 必须 Secure」会静默拒绝 dev http 的写入 → 刷新永远失败。② **refresh cookie 必须带 `expirationDate`**（bearer `TokenResponse.refresh_expires_in`，缺省 fallback 30d）——不带 = session cookie，应用重启即丢、覆盖掉服务器原本 30d 持久 cookie，变成「每次重启都要重登」。
- **CORS 源可配置**：`CORS_ALLOW_ORIGINS`（逗号分隔）取代硬编码 localhost；凭证式 CORS 禁用 `*`，须逐一列源。CORS 中间件置于限流外层，故 429 也带 CORS 头。默认已含 `app://agentcore`（桌面生产包 origin）。
- **Electron 生产包 Cookie 拓扑（✅ `app://` 方案，机制已验）**：打包后 renderer 不走 `file://`，而是自定义协议 `app://agentcore`（standard + secure origin，→ 见代码 `main/index.ts` `registerAppProtocol`；理由见 [`../04-前端/前端技术与架构.md` §7.2](/docs/04-前端/前端技术与架构.md)）。它与远端 API 跨站，故生产须 `COOKIE_SAMESITE=none` + `COOKIE_SECURE=true`（`deploy/config/production.env.example` 已配齐）；**启动期 fail-closed**：`samesite=none` 而 `cookie_secure=false` → 拒绝启动（浏览器丢弃无 Secure 的 None cookie），见 `main.py` `_validate_production_security`。dev 同站（`localhost:5173`↔`:8000`、`lax`）测不出。
  - **机制已验**：harness `apps/desktop/scripts/verify-cookies`（可复跑）在真实 `app://agentcore` origin 对跨站 HTTPS 后端跑「登录→刷新→/me」，两枚 cookie 均以 `Secure; SameSite=None` 落盘并跨站回传 → 生产拓扑成立。⏳ 残留：真实远端部署端到端复确认（候补＝改 Authorization Bearer 头，后端 `/v1/auth/token*` 已具备、手机端在用）。
- **排障口径**：「总是掉登录」先查刷新链路（Cookie path / SSE 是否接入刷新 / 轮换是否互踢——后者已由 §五 宽限窗口 + 前端单飞刷新兜住），调长 access 过期时间只是掩盖、非根治。桌面产品日志 `userData/logs/desktop.jsonl`：冷启动看 `auth.bootstrap`；中途踢登录看 `auth.session_kicked`；失败原因看 `auth.refresh`（`missing_refresh_cookie` / `http`+`message` / `cookie_write_failed` / `ambiguous_refresh_cookies`）。

Cookie 属性与实现 → 见代码 `routes/auth.py` `_set_auth_cookies`、`config/`、`.env.example`。
