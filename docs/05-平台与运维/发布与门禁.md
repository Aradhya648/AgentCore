## 七、发布策略 ✅ 已确定

> **实现现状**：`GET /livez` / `GET /readyz` / `GET /version` 已实装。部署/发版走本地脚本（§三）；GHA 仅 `workflow_dispatch` 备用（CI 在 `ci.yml`；Actions 分钟不足时以本地 `pnpm release:gate` 为准）。`/readyz` 巡检：`deploy/scripts/healthcheck.sh` + systemd timer。

### 7.1 版本钉定

**多轨道 semver**（开发期）：API（`pyproject.toml`）、Desktop（`package.json` + `desktop-v*` tag）、Web 客户端（mobile/admin build 注入 `__APP_VERSION__` + git SHA）**独立 bump**（`pnpm bump-version <track> patch|minor|major|x.y.z`）；About / 系统页双行展示「客户端版本」与「API 版本」。所有客户端请求带 `X-Client-Platform` + `X-Client-Version`（→ `scripts/client-build-info.mjs`、各端 `lib/clientBuildInfo.ts`）。

部署一律按 **git SHA**，不按浮动 `latest`。应用镜像构建期注入 `GIT_SHA` / `BUILT_AT`，运行时经 `GET /version` 暴露（端点已实装；启动入口在环境未注入时自 git 工作树补 SHA、按启动时刻补构建时间，发布流水线经环境变量注入则优先）。部署脚本传 `latest` 时，会先解析为当前 `master` 的具体 SHA 再 pin——容器跑的永远是确定 SHA（可追溯、可秒回）。

### 7.2 发布点（Release Point）

`master` 是 WIP 快照主干，**HEAD ≠ 可上线点**。用 `prod-*` tag 标记发布点（语义：「这个 SHA 是要上线的版本」）。部署以发布点为准，而非 `origin/master`——tag **仅作标记**、不触发自动部署（`deploy-backend.yml` 仅 `workflow_dispatch` 备用，§三 CI/CD 决策；漂移哨兵仍 ⏳）。

### 7.3 漂移检测

Admin 系统页 **发布漂移** 卡片（✅）：客户端拉 GitHub Latest（`AgentCore-releases`）与官网 `/api/desktop-release`，对比下载页是否滞后；控制台 SHA vs API SHA 标注「异轨/同部署」。

CI 每日自动比对线上 `/version` 与最新 `prod-*` tag（⏳ 目标；MVP 未接入）：

- prod 落后 tag → 「发了版没部署」（真漂移，告警）
- `master` 超前 tag → 「攒了未发布的 WIP」（正常，不告警）

桌面端同理：比对 `package.json` version 与公开发布仓的 `releases/latest` tag（⏳ 未接入）。

### 7.4 Deploy ≠ Release

构建/部署之上还有一层「部署 ≠ 发布」解耦——后端功能可先暗发到生产，由配置/特性开关翻开才对用户可见。支持灰度 + 最低客户端版本门控（让后端先于桌面发版，仅追上的客户端点亮）。

#### 跨轨道发布协同（2026-06 决策）

**不强制**后端与桌面（或各客户端）同一天、同 SHA 锁步发布——§7.1 多轨道 semver 的设计意图即**独立节奏 + 按需协同**。`prod-*` 与 `desktop-v*` **不绑定**；Admin 漂移卡片标注「异轨/同部署」是观测，不是告警。

| 变更类型 | 是否要快跟 | 说明 |
|---------|-----------|------|
| 纯后端（客户端无感） | 否 | skills / evals / prompt 等；桌面不必跟 |
| **协议 / 事件契约** | **是（天级窗口）** | 动了 `packages/contract-types`、protocol-conformance 向量、各端 fold → 后端 + mobile/admin **同日** deploy；桌面 **7 天内** patch 发版 |
| 纯客户端 UI | 否 | 主题 / 布局；后端不必跟 |

**判据**：本次 PR 是否改协议 fold 或事件类型？是 → 走「协议变更」行；否 → 各轨道独立发。

**协议变更轻量流程**（人工 checklist，非自动化门禁）：

1. `pnpm conformance` 全绿后再 prod deploy
2. 同日：`prod-*` + mobile/admin Pages deploy
3. **7 日内**：`desktop-v<patch>` + 官网 `FALLBACK_VERSION` + `deploy:pages`
4. 旧桌面用户：对话通常仍可用（后端向后兼容发事件），新 UI 等 auto-update；不应依赖「必须同天发桌面」来保活

**否决**：`prod-vN` 与 `desktop-vX.Y.Z` 强制同 tag / 同 SHA 发布——发布成本与回滚独立性不划算。

⏳ 远期：`min_client_version` 特性开关接线后，协议变更类功能可后端先上、仅新版本客户端点亮（§7.9），进一步降低人工记「7 天内补桌面」的负担。

### 7.5 Monorepo 选择性构建

`push master` **不自动构建/部署**（2026-06 切本地脚本，§三）。在自托管机执行 `pnpm deploy:backend <sha>` 构建 api 并推镜像仓库。⏳ 多服务 retag 优化未纳入。

### 7.6 桌面端构建与双仓发布

> **实现现状**：`.github/workflows/release-desktop.yml` 仅 `workflow_dispatch`（`platform=mac`）→ 预建 draft → **macOS arm64** 构建 → electron-builder 上传公开发布仓 `Lawofall/AgentCore-releases`。**Windows 不走 GHA**（为省额度；本地 `release:win` / 分步 `--win`）。`desktop-v*` tag **仅作发布点标记**，不触发构建。内测档位：**未签名**；Mac **arm64 only**（Apple Silicon，Intel / Universal 不在支持范围）。正式签名 + 公证 → 远期规划 §3.1（详细提案不在公开仓 / 维护者本地）。

| 环节 | 机制 |
|---|---|
| 构建触发 | Win = 本地；Mac = Actions **workflow_dispatch**（仅 `mac`）。`desktop-v<ver>` tag 仅标记，不触发 |
| 产物 | Win 本地 / Mac GHA → 公开发布仓草稿 release（人工转正） |
| 灰度 | `latest.yml` 的 `stagingPercentage` 分桶 |
| 熔断 | 后端 `DESKTOP_UPDATES_ENABLED=false` |
| 软最低版本 | 后端 `DESKTOP_MIN_VERSION` → `GET /updates/policy` 的 `min_desktop_version`（空 = `null`，不提示；生产建议如 `0.6.5`）。桌面 Electron 启动比对本地版本，低于则顶栏下可关闭软横幅（CTA → 设置·关于并检查更新）；**不**强制杀进程。web 客户端不显示。`clientVersion()==="dev"` 永不判过旧 |

**`GET /updates/policy`（现状）**：未鉴权；载荷 `{ enabled: bool, min_desktop_version: string | null }`。`enabled` 为自动更新急停闸（客户端 fail-open）；`min_desktop_version` 为软地板（拉取失败也不弹横幅）。硬闸 `CLIENT_TOO_OLD` / 特性开关 `min_client_version` → §7.9，未在此落地。

**双仓发布模型**：源码仓已公开（MIT）；安装包仍发到公开发布仓（`Lawofall/AgentCore-releases`）——双仓是**发布产物仓**分工，不是为了藏源码。Win 与 Mac 产物汇入同一 `v<ver>` draft，**Win + Mac 齐全再 Publish**（各平台资产构成见 `electron-builder.yml`；**开发期例外**：无真实用户时可仅 win 转正、mac 就绪后 `gh release upload` 补进同版本——站点缺 mac 资产自动隐藏 mac 按钮、`FALLBACK_VERSION` 暂留上一含 mac 版本，正式上线后恢复齐全再转正）。**否决** electron-builder `--publish always` 当唯一上传路径——#6676 竞态常只传上 `.blockmap`、丢掉 `.exe` + `latest.yml`；现行 `release:win` = `--publish never` → `gh release upload --clobber` → 资产断言（与 Mac GHA 同构）。

**内置 Python 运行时**：electron-builder 前先跑 `pnpm bundle:sidecar`，产物经 `extraResources` 拷入安装包；动机与按 OS 打包约束见 [双模式 §10.5](/docs/02-架构/双模式工作区.md)。CI 内 bundle 末尾的 `import agentcore.sidecar.server` 冒烟必须通过。

**原生模块（node-pty）**：`asarUnpack` 解包（`.node` / conpty DLL 在 asar 内 dlopen 失败）；`npmRebuild: false` + `nodeGypRebuild: false`——官方 prebuilds 走 N-API 直接可加载，强制 rebuild 反而在缺 Spectre 缓解库的 Win 机器上失败。新增原生依赖按此模式对齐。

**macOS 内测安装**：未签名——首次打开须**右键 → 打开**（或 `xattr -cr`）；自动更新经 zip + `latest-mac.yml`，`quitAndInstall` 后可能需再次右键打开。

发布步骤命令 → 见下文 §本地发布操作手册「桌面发版」。**真机 QA 要点**（Apple Silicon，Rosetta 不算）：安装可启动 → 登录 / SSE 流式 → 绑定本地文件夹（sidecar 内置 Python）→ 本地回合文件读写 → 自动更新能发现新版本。

→ 见代码 [`.github/workflows/release-desktop.yml`](/.github/workflows/release-desktop.yml)、[`apps/desktop/electron-builder.yml`](/apps/desktop/electron-builder.yml)、[`apps/desktop/scripts/bundle-sidecar.mjs`](/apps/desktop/scripts/bundle-sidecar.mjs)、[`apps/desktop/src/main/updater.ts`](/apps/desktop/src/main/updater.ts)

客户端自动更新行为（检查频率 / fail-open / 双通道）见 [`../04-前端/前端技术与架构.md` §7.6](/docs/04-前端/前端技术与架构.md)。生产 API 指向你的 `https://app.example.com/api`（或品牌域名等价物）。

### 7.6a Android APK（官网侧载）✅

> **实现现状**：本地 `pnpm -C apps/mobile release:android`（需 **JDK 21** + Android SDK + `keystore.properties`）→ 签名 APK → `gh release upload` 到同一产物仓 → `sync-release-cdn --android` 写品牌域 `downloads.*/android/`。tag 轨 **`android-v<ver>`**（与桌面 `v<ver>` 分轨）；资产名 `AgentCore-<ver>-android.apk`。官网 `/download` 另查含 `*-android.apk` 的非 draft release，**有资产才露下载链**。App 内软提示「去下载」（打开 APK URL），不强制、不做壳内 OTA。操作清单 → [`apps/mobile/README.md`](/apps/mobile/README.md)。

| 环节 | 机制 |
|---|---|
| 构建触发 | 仅本地；无 GHA 自动触发 |
| 签名 | `android/keystore.properties`（gitignore）；缺则脚本拒绝打 release |
| 产物体积 | Capacitor 壳（系统 WebView）压缩后约数 MB 属正常——**不含** Chromium / sidecar |
| 官网 | `releaseArtifacts.mjs` 的 android 三字段 + `DownloadPanel` |
| CDN | `downloads.*/android/AgentCore-<ver>-android.apk` + `latest.json`（App 内更新读此） |
| App 更新 | 原生 Android 拉 CDN `latest.json`；`dev` / 网页壳不提示 |
| CORS（生产必配） | Capacitor WebView origin = **`https://localhost`**（另保留 `capacitor://localhost` / `http://localhost`）。缺则 App 报「无法连接后端」——`CORS_ALLOW_ORIGINS` 须含上述三项（见 `production.env.example`；改后 recreate api） |
| FCM | **无** `android/app/google-services.json` 时 `release:android` 注入 `VITE_PUSH_ENABLED=false`，**禁止**调用 `PushNotifications.register()`（否则原生闪退，JS catch 不住）。有该文件才开推送 |

**真机 QA**：安装启动 → 登录 / SSE →（有 FCM 时）「需要你」通知与深链；卸旧包或覆盖安装新 `versionName`。

→ 见代码 `apps/mobile/scripts/release-android.mjs`、`apps/website/functions/_lib/releaseArtifacts.mjs`、`deploy/scripts/sync-release-cdn.mjs`、`deploy/scripts/add-capacitor-cors.mjs`（运维补 CORS 用）

### 7.7 备份与恢复策略

**只备不可重建的主数据**——PostgreSQL + 对象存储（工作区文件）。Redis 是缓存丢了自愈。

| 原则 | 说明 |
|---|---|
| 迁移前快照 | 每次 `alembic upgrade` 前自动 `pg_dump`，失败即终止迁移 |
| 破坏性干净恢复 | 回灌前 `DROP SCHEMA public CASCADE`（非空库直接灌会主键冲突） |
| 停应用再恢复 | 避免并发写入；恢复后不自动起应用（需重新 deploy 对齐版本） |
| 异地副本 | 默认只有本地——防不了整机损坏，放量前必须开异地 |
| **灾备演练** | 备份未验证过恢复 = 没有备份。放量前必做一次完整恢复演练 |

**脚本已入仓** → 见 `deploy/scripts/backup.sh`（全量备份 + 轮转）/ `restore.sh`（破坏性干净恢复：完整性校验 → 确认门 → 停 api → 回灌 → 不自动起）/ `deploy/systemd/agentcore-backup.*`（每日定时 oneshot）。**当前仅覆盖 PostgreSQL**（DATA_DIR 文件 / 对象存储需另行文件级备份）；异地副本与灾备演练仍为运维动作（参数/排程见脚本与 runbook）。

### 7.9 特性开关架构（⏳ 目标设计 · 未实装）

特性开关是 §7.4「Deploy ≠ Release」的落地机制——后端代码先暗发到生产，由配置翻开才对用户可见。**实现现状**：本节为已确认目标设计，服务端三门求值 / 灰度分桶 / `min_client_version` 接线均 ⏳ 未建（现仅有 `desktop_updates_enabled` 熔断与 `config/features.py` 编译期垂直开关；`api/routes/system.py` 注释预留接缝）。

**服务端求值**：灰度/版本逻辑只在后端运行，客户端与后端代码路径都只读「已解析的布尔」。理由：求值逻辑不泄漏到端、各调用方判定一致、单一真相源。

**三道门顺序求值**：每个 flag 按以下顺序判定，任一道关闭即最终为 `false`：

| 门 | 含义 |
|---|---|
| `enabled` | 总开关（关 = 永远关） |
| `min_client_version` | 仅 ≥ 该版本的客户端可见（跨列车安全阀） |
| `rollout` | 灰度百分比（0–100），按稳定 key 分桶 |

**跨列车安全阀**：`min_client_version` 让需要新客户端支持的后端功能先进生产，仅追上版本的客户端点亮——将「后端先上、桌面后放量」的跨列车顺序约束变成开关里的硬门，而非靠人工记顺序。

**分桶策略**：优先用户 `user_id`（同一用户跨设备判定一致），未登录回落到设备 `client_id`（UUID 持久化）。同一 key 永远落同一桶（不抖动），按 flag 加盐避免不同 flag 命中同一批人。登录成功后需重拉开关以纠正分桶 key 切换。

**fail-safe vs fail-open 对偶**——刻意相反的失败行为：

| 机制 | 失败兜底 | 为什么 |
|---|---|---|
| 特性开关 | **fail-safe（默认关）** | 未发布的功能要保守，不能因后端抖动误开半成品 |
| 桌面自动更新 | **fail-open（默认开）** | 已发布的安全网络要保活，可远程熔断 |

**演进预留**：v1 配置驱动（翻转需重启），运行时即时翻转（Redis/DB override）为 v2 注入缝。

## 九、工程门禁与结构治理 ✅ 已确定

> 用 CI 不变量替代人工纪律，防止多 Agent 并行开发下行为回归/类型债/结构腐化悄悄累积。

### 核心哲学：棘轮（Ratchet）

基线 = 当前现状，落地当天全绿，只拦新增腐化。修好真问题就收紧基线（只降不升），放宽必须在 PR diff 里显形并给理由。

### 三道门禁

| 层 | 拦什么 | 策略 |
|---|---|---|
| **行为回归** | 后端 lint + 测试，前端类型检查 | 合并前 CI 硬阻塞 |
| **类型债** | tsc strict / mypy strict | 棘轮：逐文件计数基线，不允许新增错误。棘轮终局 = 修到零 → 升为硬门禁 |
| **结构治理** | god-file 膨胀、模块漏文档 | 行数棘轮（超标存量登记天花板）+ 模块文档守卫 + 清单守卫 |

### 跨端契约门禁

> **实现现状**：✅ 已写入 `ci.yml` 的 `contracts` job（"Contracts + conformance (gen + drift gate)"）：`node scripts/gen-types.mjs`（重生成 REST + SSE 契约产物）+ `agentcore.conformance.export`（重生成一致性夹具）+ `git diff --exit-code`——committed 产物与真相源漂移即红。若 Actions 分钟不足、CI 未跑，发布前本地跑这三步（或 `pnpm release:gate`）核对 0 diff。

后端改 schema / SSE 事件必须重新生成前端类型并提交，`git diff --exit-code` 拦截 generated 静默漂移（目标）。覆盖两条契约：

| 契约 | 真相源 | 生成产物 |
|---|---|---|
| REST | OpenAPI schema | `openapi.ts` |
| SSE | 后端 EventType + payload dataclass | `sse-events.ts` |

`task gen:types` 一次重生成两者。根除「后端发了新事件/字段、前端 union 或 interface 漏抄、功能静默装死」。

### 拆分实操经验

- **facade + 子包**：按子域拆，`__init__` 全量 re-export 保持公共 API 不变 → 调用方零改动
- **mixin vs 协作者类**：跨切面、读写宿主多字段的状态逻辑用 mixin——经 MRO 保留 `self._x()` 调用、零调用点改动
- **棘轮行数口径**：脚本内自产自校，CI 与基线自洽；勿用不同工具对账（口径不同）
- **陷阱**：移动挂着门禁的文件要同步硬编码路径，否则门禁静默失效
