# 对话日志分析指南

> **Why**：产品 AI 回合的结构化事件在 `logs/dev.jsonl`（JSONL），完整正文在 Postgres——查失败回合靠 **trace_id 全链路**，不是搜 Cursor 转录。
>
> **How（操作步骤权威）**：用户给出 32-hex / UUID / 排查包时 → **先读** [`.cursor/rules/conversation-logs.mdc`](/.cursor/rules/conversation-logs.mdc)。本文不重复 CLI / 手工查询长文。

## 接缝（日志 ↔ DB）

| | 产品 AI 日志 | Cursor IDE 会话 |
|---|---|---|
| 位置 | `logs/dev.jsonl`（仓库根；20MB 轮转） | `agent-transcripts/`（与产品无关） |
| ID | `trace_id` = **32-hex 无连字符**；`conversation_id` = UUID | 文件名 = 带连字符 UUID |

- **全链路键**：`trace_id`（同一次用户交互，含进程内委派）；会话 → `conversation_id`；单次回合运行 → `attempt_id`；持久回合 → `message_id`（≡ journal `turn_id`）。
- **DB join**：`messages` / `cost_events` / `run_sessions` 带 `trace_id`（assistant / 落账有值；user / handoff 常为 `NULL`）。键集合权威 → [后端架构 · Context 注入](/docs/02-架构/后端架构.md)。
- **不落完整正文**；`preview` / `reply_preview` ~200 字；`LOG_LLM_BODIES` 开时有截断脱敏 `llm.request`/`response`。
- **模块入口**：事件注册表 `observability/catalog.py`（`sync_log_event_registry.py` 生成）；查询层 `observability/query/`；CLI `log_timeline.py` / `log_stats.py`。新增埋点写 `logger.info("component.action", …)` 后 sync——**勿手改**下方事件表。

## 委派验收事件（binding vs overlay）

排查 `delegate.acceptance_resolved` / `delegate.completion_criteria_unmet` 时：

| 字段 | 语义 |
|---|---|
| `criteria` | **仅 binding kind**（显式 / 结构化交付解析出的批次验收）。省略未绑定时为 `null`——**不是**伪 kind（历史上曾误写 `typescript_verify`）。 |
| `gaps`（仅 unmet） | 可含 binding 缺口 **以及** TS 落盘强制验证、import 图闭合等 **overlay** 文案；勿把 gaps 里的叠加当成「criteria 漂移」。 |
| `execution_id` | 同执行图 join 键。`acceptance_resolved` 在 kickoff 时若 context / 追加宿主已有则写入；`unmet` 收尾必带。缺 id 时用同 `trace_id` + 时间邻近辅助对齐。 |
| `source` | 绑定来源（如 `explicit` / `structured`）；与 kind 正交。 |

**禁读法**：跨批次 / 跨 `trace_id` 拿两边的 `criteria` 字符串差分当「验收漂移」——overlay 批次常见 `null`，与显式 `code_verified` 并存是正常现象，不是 resolve 优先级 bug。

## Phase-0 字段（代码看不出来）

`chat.turn_complete` 的 `prepare_ms` / `assemble_ms` / `ttft_reasoning_ms` / `ttft_content_ms`：**缺路径为 `null`，勿当 0**。TTFT 只记 captain 首 stream；非 `llm.call.latency_ms`、非整回合 `duration_ms`。详释与排查配方 → `conversation-logs.mdc`。
