## 核心定位

执行引擎是 CEO 主 Agent 与 worker 实例之间的调度中枢。它接收 CEO 经 `delegate` 下达的子任务（`build_run_plan` 据 `depends_on` 建 DAG），解析依赖图，管理 worker 生命周期，协调并行/串行执行，处理失败与取消，并向 UI 推送实时状态更新。

## 一、基础概念（DAG 调度）

> DAG 调度概念提要；运行时以 §二~§四 / §八 已落地主体为准。以下只保留代码看不直观的设计约定。

### 步骤状态与调度

计划是 DAG：每个 step 声明 `depends_on`，执行引擎扫描「依赖已满足且未启动」的 step 并发启动（受 `max_parallel` 限制）。步骤状态 `queued → running → completed`，异常分支 `failed` / `skipped` / `cancelled`（枚举见 `runtime/runs/types.py` 的 `RunPhase`；失败重试由 `RunPolicy.on_failure=retry` 在 `runs/wave.py` 内部完成（硬上限 3 次退避），对外仍以 `FAILED` 收口并 emit `run_failed`；**扇入默认宽松（取消≠失败）**：有依赖节点默认 `require_upstream=false`——**≥1 个上游成功交付即运行**，缺席上游以「前置缺席」块注入其任务输入（`runs/executor_context.py`，禁止编造该路结论；防单上游取消把汇总员整个拖掉）；**零成功上游且存在硬缺席**（取消 / `skip`·`retry` 用尽失败 / 级联跳过）才跳过，`FAILED`+`degrade` 属软缺席仍放行；`require_upstream=true` 恢复严格语义（任一上游取消/失败即级联跳过，禁止汇总节点消费残缺产物时显式声明）；`force_continue=true` 零成功仍放行；CEO 亦可 `replaces_run_id` 重派后复活；CEO 经 `replaces_run_id` 补派时改写下游 `depends_on` 并复活被级联跳过的节点，使其等待替换后的成功上游。级联跳过 / stop 后未跑尾部物化为 `SKIPPED` 并 emit `run_skipped`、中途取消（redirect/stop/超时硬收尾）emit `run_cancelled`——二者均 DURABLE，重载图上呈「未执行 / 已停止」而非假排队/假运行。并发模型为 asyncio 协程——多 Agent = 多 asyncio Task 共享事件循环（Agent 本质是 I/O 密集的 LLM 调用，协程足够）。

> **调度埋点量化 ✅**：为验证连续调度「让并行真正发生」，每次 run 回灌 `BatchMetrics`（无晚绑定·escalation·checkpoint 的 plan 全为 0）。**设计取舍**：用 `metrics_sink` 而非返回值或直接打日志——调度器对宿主无感、cancel 路径不回灌。`slot_starved` 计**真实排队事件**（连续饥饿 episode），与 50ms cancel 轮询解耦。活图 merge 追加节点后**重算**并发宽度（仍受全局 `max_parallel` 与树预算约束）。→ 见代码: `runtime/runs/wave.py`

### 检查点决策语义

> **本篇权威**：检查点 / `plan_review` / 2b 续跑语义以本节与 §暂停与恢复 为准；编排器、协作模式等文档仅外链此处。

检查点分两类，**实现现状不同**：

- **CEO `ask_user` 检查点（✅ 已落地）**：CEO 主动调内置工具 `ask_user` 暂停回合征询用户——CEO **唯一的发问原语**（开场引导与途中拍板共用一卡一机制）。语义、字段与阻塞/非阻塞矩阵见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。载 `message`（必填）+ 可选 `context` / `assumptions` / `questions` / `style_options`；桌面端以提交/停止两态作答，答复回流 CEO ReAct 循环；`stop` 走 `ToolResult.terminal` 优雅收口。**挂起即收口（②）**：到达检查点即**落帧并收口终止**（`ToolEffect.SUSPEND → FinishReason.PAUSED`，进程内 resolve Future 永不 park），经**单一冷路** `POST …/resume` 续跑——不再 `POST …/interactions` 原地解析；问答入 journal 可回放。属 `ToolCategory.INTERACTION`（非 ORCHESTRATION），仅在 `settings.checkpoint_gate_enabled` 且有交互用户时装配，worker 路径不给。
- **DAG `checkpoint_after` 结构化挂起（✅ Phase 2a 已落地）**：step 带 `checkpoint_after` 且 `COMPLETED`、下游仍待跑时，`WaveScheduler` 在波间 `await` `plan_review` 交互（`kind=plan_review`，continue/adjust/stop——adjust 把备注作为 steer 注入未跑下游的 `RunSpec.steer`、由 executor 渲染为最高优先级指示块；stop/abort 后未跑尾部统一标 `SKIPPED`）；**挂起即收口（②）**：检查点在波边界**落帧并收口终止**（`SUSPEND→PAUSED`），不再 `POST …/interactions` 原地解析，且**仅顶层 `depth==0` 设检查点**（嵌套子团队直接放行）；事件 `plan_review_required`/`plan_review_resolved` 入 journal 可回放；前端见 [`前端UX设计.md` §三/§五](/docs/04-前端/前端UX设计.md)。**✅ 2b 已落地**：turn 级落盘（`paused_turns` 帧）+ `POST …/resume` 续跑（**纠正设计：不加** `RunPhase.PAUSED` 第三终态，回合级落盘，见 §暂停与恢复）。**协调态例外**：有 `CoordinationSession` 时波边界只发 `BOUNDARY_YIELD`（不写 `TurnSuspension` / 不 seal / 不发 `plan_review_required` 收口）；用户拍板走 `ask_user`。⏳ 余项：跨进程 Redis（多 worker）+ 治理强制层（声明即必停、非 CEO 自声明，见 [`../06-规划/远期规划.md` §2.3](/docs/06-规划/远期规划.md)）。

> **勿与工具审批混淆**：`approval_required` / `approval_resolved` SSE 事件**不是**检查点，而是**工具审批闸门**（GRANTABLE 工具暂停待用户授权），已落地（按 `settings.approval_gate_enabled` 开关）。CEO 自身不持 `GRANTABLE` 工具，故实际在**本地模式 worker** 层生效（worker 继承 CEO 门，双模式 P2d；`worker_gate_applies` 仅 local 为真）；云端执行类工具按**沙箱→审批姿态**分流（`runtime/sandbox_approval.py` 三态：local → `REQUIRES_AUTH`、云端无沙箱 → `UNAVAILABLE` 不注册、`GVISOR_ENABLED` → `AUTO_PASS` 免审批）。审批语义与策略表见 [`../05-平台与运维/安全权限与治理.md` §三](/docs/05-平台与运维/安全权限与治理.md)。审批 / 本地工具 / worker 升级 / 辩论轮共用 `runtime/interaction.py` 的 `InteractionRegistry`（§8.6 ClientRequestBridge）同构挂起-恢复，单一 resolve 端点 `POST …/interactions/{id}`（按 kind 判别）；**`ask_user` / `plan_review` 检查点已挂起即收口（②）**——改走 `POST …/resume` 冷路、其 resolve schema 已从该端点移除。

> **开工提案卡是 `ask_user` 的一种形态**：开场与途中共用同一挂起机制。→ 见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。

### 受监督的波循环（晚绑定 + 边界让出）✅ 已落地

> **本篇权威**：晚绑定 / 波边界让出 / `replan` 续跑的**执行语义**以本节为准；CEO 侧 `replan` 工具形态见 [`编排器与CEO主Agent.md` §一 `replan` 原语](/docs/03-AI核心/编排器与CEO主Agent.md)。

**解决的痛**：worker 职责在 CEO `delegate` 那一刻就绑定死，但下游真正要干的活往往得等上游产物落地才清楚——团队闷头按可能过时的初始计划做完（「计划漂移」）。把执行模型从「CEO 下完计划即缺席」改为「**CEO 是波边界的监督者**」：`build_run_plan` 一次建全 DAG（开局全貌可见），节点可**晚绑定**，`WaveScheduler` 自主跑波、只在**决策边界**把控制权交回 CEO 定稿 / 纠偏后续，续跑同一张图（不重建）。这是 §一 检查点语义的推广——检查点只是边界的一种。

**形态**：

- **晚绑定节点**（`RunSpec.bind_after_deps`）：spec 关键字段先占位，依赖落地后由 CEO 在边界定稿（复用 `steer` 的 in-place mutate 范式）；`_select_ready(defer_bind=)` 绝不调度未定稿节点。
- **边界判据**（`BoundaryReason ∈ {CHECKPOINT, BIND, SCOPE}`）：① `checkpoint_after`（让用户把关）；② 依赖已就位、待定稿的晚绑定节点（让 CEO 定稿）；③ 已完成节点带未消费的 `escalate kind=scope` 偏离信号（让 CEO 纠偏）。
- **边界结果**（`BoundaryOutcome ∈ {PROCEED, YIELD, ABORT}`）：`YIELD` = 软暂停（复用 `should_stop` 语义：排空 in-flight、返回 partial、尾部不 skip），把控制权交回 CEO 主循环。
- **续跑**：`delegate` 的 `_drive` 收到 `YIELD` 返**非终态** ToolResult（CONTINUE）+「计划已让出」简报给 CEO，暂存 `(plan, completed)`；CEO 经 `replan` 定稿 / 纠偏 / 追加 / 收口后，`_drive(seed_completed=…)` 续跑同一 DAG。

**双臂：同一边界，让给用户 or 让给 CEO**（按影响力分档，对齐 `ask_user` / checkpoint 心智）：

| 臂 | 触发 | 谁裁决 | 用户感知 |
|---|---|---|---|
| 让给 CEO（BIND / SCOPE） | 低杠杆：晚绑定定稿、据 escalate 微调下游 | CEO 自主 | **无感**（仅图上「计划已调整」轻痕迹——`plan_revised` 折到节点徽标「职责已定稿 / 方向已校准」，不打断，见 [`../04-前端/前端UX设计.md`](/docs/04-前端/前端UX设计.md)） |
| 让给用户（CHECKPOINT → `plan_review`） | 高杠杆：选错会让用户明显不满 / 推倒重来 | 用户 | 决策卡，挂起待答（见上「检查点决策语义」）；**协调态例外**：只发 `BOUNDARY_YIELD`，用户拍板改走 `ask_user` |

> **复用而非另起炉灶**：两臂共用 `WaveScheduler` 的边界机制 + §8.2 唯一挂起原语；让给 CEO 的臂本质是调度器在边界把控制交回 CEO 的 ReAct 循环、续跑同一 DAG——**不新增挂起子系统**、**不增委派深度**、**不碰 worker↔worker 直连**。CEO 臂走正常回合生命周期（非终态返回 = 普通 ReAct 续跑），plan / completed 由 journal 投影重建，**不需新 durable 挂起**（区别 user 臂的 `paused_turns`）。

> **偏离信号：复用 `escalate` + 轻量 `kind=scope` / `kind=dep`**：worker 发现自己 / 下游 scope 错了（`kind=scope`），或卡在一个**还不存在**的输入 / 依赖（`kind=dep`），用现有 `escalate`（**非阻塞**）加一个提示位上报（**扩展而非新原语**）；两者**同走反应臂波边界**（`_scope_pending` + `BoundaryReason.SCOPE` 一处机器）被 captain **一等消费**——`scope`→操舵已有下游、`dep`→`replan(add)` 追加产出者。**否决**「为 scope/dep 单立信号 / `InteractionKind`」：决策的是 captain、worker 只供偏离事实，单立 = 与 `escalate` 高度重叠（补丁绊线）。kind 轴语义见 [`Agent协作模式.md` §二·escalate](/docs/03-AI核心/Agent协作模式.md)。

> **成本纪律（不变量）**：无晚绑定 / 无 escalation / 无 checkpoint 的 plan，调度器一路跑到 terminal、一次 `delegate` 返回（= 今天行为、**零新增 CEO 回合**）——**CEO 回合数 = 真实决策点数，不是波数**。
>
> **协调模式例外（✅）**：≥2 worker 默认协调时 CEO 波内存活，`delegate` 立即返回；同回合再调 `delegate` 往同一张协作图追加（**一张图一个 `execution_id`**），不必等全队完成。**跨回合**经 `append_to_execution_id` 复用旧 id 继续生长（事件 `graph_append` 锚点落新回合；生长帧续写宿主 `turn_journal`；图收口不绑新回合 `message_end`）——见 [`编排器与CEO主Agent.md` §自选粒度](/docs/03-AI核心/编排器与CEO主Agent.md)。**异步团队模型**：协调 session / 后台 drive 与聊天回合生命周期解耦——**SSE 断连** teardown 不关闭仍活跃的协调、不借用回合 LLM client 给后台 worker（drive 自建自关独立 client）；**显式 user `/stop`** 级联取消 drive 与在跑 worker（已完成产出保留）。**产出投递（批次 1）✅**：DURABLE 展示事实经 execution 宿主 journal 落盘（不依赖回合 sink）；对话级执行注册表为路由唯一源；无附着回合的终态由收割者发起系统收口回合投递终稿；协议事件 `execution_detached` / `execution_completed`（详见 [`编排器 §协调模式`](/docs/03-AI核心/编排器与CEO主Agent.md)）。空转巡查在注入前检查 worker 活性（in-flight → 不发假 nudge、短等后让出 CEO）；同构再委派默认拒绝（须 `force`）；增量合并同样过开工卡。成本纪律重定义为「协调回合 ≤ 必要决策点 + 事件合并窗口」（中间完成可合并；预算分**进度池 / 决策池**两本账作**纯遥测计数**——批次 4 起不再以进度池耗尽 HOLD 唤醒；合并窗口仍攒批例行进展；决策/必要点分类只影响合并与遥测口径——见 `coordination/session.py` `split_coordination_budget` 与 `coordination/wait.py`）。显式 `coordinate=false` / 单 worker / finalize / 嵌套 lead / **批含 `checkpoint_after` 且 checkpoint 闸开**（B1：把关卡须 durable 弹给用户，走经典阻塞）仍守上文零新增纪律。

> **turn 末仍开着的 supervised run**：CEO 拿到让出简报却没 `replan` 就结束回合（最终答复 / `MAX_ROUNDS` / 上游报错），则 turn 末按**隐式 `stop`** 收口（折算已完成工作 + 未跑尾记 SKIPPED + 释放暂停态），避免团队工作悬空漏计费 / 来源不显；无让出时 no-op。

> **持久化与跨端一致**：晚绑定占位、scope 的 `kind`/`consumed` 经快照往返保真——重建的暂停计划仍知该节点待定稿、**绝不未绑定就 dispatch**；`YIELD` 给 CEO 走内部续跑（不产生用户可见事件分类），`replan` 改图走 `plan_revised` 事件（入 journal 可回放、三端等价）。

> **对任何 captain 一致（lead 子树同享）✅**：受监督波循环不是「根 CEO 专属」——子 lead（`depth < 2` 默认带队）经 `LeadSubteam` bundle 同获绑到自身 `child_delegate` 的 `replan` + 收尾折账，故 lead 也能在自己子树上「晚定稿 / 据偏离重规划」，去掉「只有根能 replan」的特例。工具形态与铸厂分层见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)。`plan_revised` 按 `run_id` 折到正确子节点、子层共用父 `execution_id` 不串层。**协调模式 scope 例外**：非阻塞协调仅根 CEO（`depth==0`）；lead 仍阻塞 `delegate`。

> **被否决 / 暂不做**：① **worker 实体化**（临时角色 → 稳定专家实体，Phase 2，用户按下）——守在「CEO 在波边界监督」一层，对齐「无团队选择器 / 每回合自适应组队」赌注（见 [`编排器与CEO主Agent.md` §六 Agent 实体化](/docs/03-AI核心/编排器与CEO主Agent.md)）；② **2b 波内抢占 / CEO 波内重入**——默认阻塞路径仍「波内无活着的 CEO」，用波边界让出替代；**协调模式下** CEO 波内存活，阻塞 escalate 改走 CEO 仲裁（`resolve_escalation`，非 worker 抢占）；③ **运行期软护栏**（类比 `delegation_nudge`）——边界结构性决策后基本不需，「实测漏触发率高再加」。
>

### 失败与取消

可重试错误（超时 / 429 / 5xx）退避重试；不可重试错误跳过该 step 或升级用户。DAG 节点失败策略（`RunPolicy.on_failure`）：

| 策略 | 行为 |
|---|---|
| `retry`（默认） | 调度器内退避重跑；用尽仍 `FAILED` 后按扇入规则处置下游（严格节点级联跳过；宽松节点凭其余成功上游照跑，见 §一「扇入默认宽松」） |
| `skip` | 失败即按同款扇入规则处置下游 |
| `degrade` | 记录失败、下游照常启动（显式最佳努力；宽松扇入下属软缺席） |
| `abort` | 排空 in-flight 后停止整波 |

**否决**：把「上游须 SUCCESS」写进 ready 谓词——失败节点永不变 `COMPLETED`，下游会死等，且与 merge 重派新 worker id、不改写旧 `depends_on` 的机制冲突。正确路径是（严格/零成功时）级联跳过 + `replaces_run_id` 改边复活。→ 见代码：`runtime/runs/wave.py`、`runtime/runs/plan.py`（`clear_revivable_skips`）。完整收敛治理（重试 / 熔断 / 早停 / 反思）见 §四。

### 录制与回放（通用事件源 · dev 能力）✅ 已落地

**回放 = 同一事件契约（SSE 事件序列为唯一真相线）的另一种事件源，不是另一条执行链路**（2026-07-17 拍板，演进自 demo tape 私有实现）。业务模块（编排、工具、前端 fold、journal）只认识事件契约，不出现「若 demo 则…」的语义分叉；挂起/恢复/正文重灌等**执行语义只有 runtime 一份实现**。

**分层职责（决策层）**：录制 = EventSink 纯 tap（失败不影响回合，默认关）；事件文档 = 线上契约超集（读时兼容旧字段、录制永不带 `projected`）；裁切 = durable-face 过滤 → 脱敏 → golden（与手写向量同判）；回放 A=FOLD（永不 remint）与 B=SINK（可 remint）互斥。操作手册 → [`demos/README.md`](/demos/README.md)。→ 见代码: `demo_tape/`

**纪律红线**：回放/演示代码**不得侵入 runtime 语义层**，只能以 tap（录）/ source（播）身份存在——禁止暂停帧私藏正文副本、私造 message 生命周期、`if is_demo_tape` 改语义。divert 标记（`is_demo_tape_frame` / `DEMO_TAPE_FRAME_KEY` 存幕内事件游标 + 冻结的 `turn_index`；绑定文件另持幕游标）是**入口分流**：决定「事件从哪来」，不改「事件如何被执行与结算」。带真实副作用的客户端工具请求（`workspace_op` / `board_op` / `board_read` / `desktop_notify`）导出期硬剪 + 断言拒收（防剪辑表漏改）；交互点 demo 模式等真人在 UI 续——冷路三 kind（`team_preview` / `checkpoint`/`ask_user` / `plan_review`）真挂起落帧；热路 `approval_*` 真挂起等热 resolve（录制 `approval_resolved` 导出剪掉、回放现场重发；APPROVE/DENY/ALWAYS 均按录制续播不分支）。播放侧对未接线 pause 仍保留 warning 兜底，但「磁带播不好」的主门禁已前移到导出。

**legacy 例外（有退役条件）**：存量 v1 磁带录制于 runtime captain 工具 display/trace 拆分之前，CEO 自持 `tool_use_*` 带 `run_id`；SINK 准备路径经 `replay/legacy.py` 集中剥离以对齐渲染契约。新录制天然无此问题；v1 磁带退役时该模块一并删除，勿扩散成通用投影旁路。

**边界**：不做全系统 event sourcing（不以事件日志重放重建领域状态）；与生产 attach / 重连回放（SSE `id:` / `Last-Event-ID` + journal-backed 回放，见 §执行与请求解耦）**正交不合并**——后者是同一 live 回合断线续看的生产可靠性面，本能力是录制文档的跨回合再消费。**不建独立工具替身层**（已拍板）；将来「全链路回放」若要对有副作用的服务端工具（搜索/git 等）短路，落点 = `execute_tools` 缝按 `tool_call_id` 用录制 I/O 返回——✅ 已确认方向、⏳ 当前不实施。

### 回合级「下一步推荐」(CEO→用户) ✅ 已落地

**定位**：回合收尾后预测用户最可能想做的 2-4 件事，作为可点选的快捷追问挂在**对应那一条**助手回复下（点选即回填输入框、可改后发）。是 worker→CEO「交接简报·建议下一步」的用户侧对偶：那条把队员建议上交 CEO，这条把整回合的自然后续下达用户。

**关键契约**：仅 `end_turn`+非空正文才 mint；payload 必带 `message_id`（缺则 no-op）；DERIVED 落 `Message.followups` 列（persist-then-signal，与 title 同辙）；best-effort 不阻断回合。→ 见代码: `memory/followups.py`

### 长对话压缩（compaction）✅ 已落地

**定位**：不是防溢出（DeepSeek 1M 不溢出），而是治两件事——**context rot**（超长上下文质量随长度下降，与缓存无关）与**缓存失效成本**（exact-prefix 缓存有 TTL，慢节奏 / 隔夜回来全量重算长历史真烧钱）。稳态成本已被前缀缓存软化，故此项是**质量项、非紧急**。

**做法**：把**早于 recency 窗口**的旧轮折叠成一份结构化滚动摘要（已确立事实 / 决策 / 未决问题 / 文件路径，逐字保留标识符·数字·路径），回合改喂 `[摘要] + 最近若干轮原文`。

**关键契约**：input tokens 越阈 → 收尾 fire-and-forget 压缩；`compacted_through` 水位幂等；摘要**算一次落库跨回合复用**（禁每回合重算打穿前缀缓存）；失败不写空摘要。压缩只作用于 CEO 窗口，**不读**进记忆整合。→ 见代码: `conversation/compaction.py`

### 回合内工具结果清理（clear_tool_uses）✅ 已落地

**定位**：与「长对话压缩」同治 **context rot**，但**作用域正交**——压缩跨回合折叠旧 user/assistant 文本，本机制**回合内**收掉堆积的工具结果。一个长 worker run 会反复 `file_read` / `grep`，旧结果每轮原样重发（token）且把窗口塞满陈旧读（rot）；而按「历史重建原则」工具 I/O **不跨轮回放**、压缩也从不见它，故单个长 run 内的工具堆积**只有本机制治**。

**做法**：在**发给模型的窗口**里，把滑出「最近 `keep_recent` 个同类结果」窗口、且本身 ≥ `min_chars` 的旧「只读可重取」工具结果，折成紧凑稳定指针 `[已清理: file_read(path='…') 原 N 字符，可重取]`。**纯投影**——只在 `build_request` 那一点改发给模型的视图。

**关键契约**：条数窗口 + 体积下限触发；投影**不改** messages/journal；resume 同输入同投影；只清 investigation 白名单只读结果。→ 见代码: `runtime/engine/tool_clear.py`

**写参清理（write_args_clear）✅**：与上正交——写工具回执本就短，但 assistant args 仍携带落盘全文致后续轮 cache_miss；有 tool result 后把 args 内大 body 折成稳定 stub（保留 path）；同样只投影、不动 journal。→ 见代码: `runtime/engine/write_args_clear.py`

### Trace 关联

> **实现现状**：✅ 进程内全链路已落地——`trace_id` 在回合起点铸一次（`core/log_context.py`），contextvars 随委派 worker 子 task 自动传播，且已落库作 DB↔日志 join 键（`messages` / `cost_events` / `run_sessions` / `turn_journal` 等带 `trace_id` 列）。权威说明见 [`后端架构.md` §Context 注入](/docs/02-架构/后端架构.md)。⏳ 仅跨进程传播（Redis / 消息总线 payload 串 trace）随「跨进程委派」一并留待，见 §8 ⏳ 项。

## 四、ReAct 循环与收敛治理 ✅ 已确定

> **不变量**：轮次上限 `ModelProfile.max_rounds`（Worker 另叠累计 token 硬顶 backstop，见收敛治理表 + 「到顶收口」）；收敛治理 `LoopController`（滑窗机械循环 → NUDGE/FINALIZE、工具失败熔断、无产出早停、反思注入）；交付前核验 `finish_guard`（done 点纯代码轻层守卫、未过回炉，见下）；引擎级工具超时兜底；空响应同模型重试至阈值后 DEGRADED、LLM 硬失败直接 ERROR/DEGRADED 收口；GRANTABLE 审批在 worker 层 gate（CEO 不持 GRANTABLE）；回合内工具结果清理（旧只读结果在 `build_request` 前投影成指针，纯视图不动 `messages`/journal，见 §三）。✅ 结构化 `RoundOutcome`/`LoopDirective` 协议（每轮产出归一为 `RoundOutcome`，治理只回一个 `LoopDirective`，主循环退化成单一 `match` 执行器）。→ 见代码：`engine/loop.py`（`react_loop`）、`engine/outcome.py`、`engine/directive.py`、`loop_controller.py`、`runtime/verify.py`。

### 基本循环

`message_start` 后逐轮迭代至 `profile.max_rounds`；✅ GRANTABLE 审批挂起；✅ 工具超时兜底（B1）；✅ 空响应同模型重试后 DEGRADED / LLM 硬失败直接收口 / 工具失败熔断 / 无产出早停 / 反思注入（B2，见下表）。✅ **结构化轮协议**：每轮先组装 `RoundOutcome`（content/reasoning/usage/tool_calls/tool_results/attempts/terminal_handoff/llm_failed 的单一事实对象），治理函数（`decide_no_tool_round` / `govern_after_tools` / `decide_llm_failure`）各回一个 `LoopDirective`（`Continue`/`Rework`/`Finalize`/`Return` 密封联合），主循环对其做穷尽 `match`——取代旧的字符串 `kind` / `terminal` 哨兵 / `LoopExit | None` 散落控制流。

### 协调事件注入（CEO 协调模式）✅ 已落地

根 CEO 进入协调后，`react_loop` 轮间从 `CoordinationSession` 取事件合并为 user 侧简报再 think。escalate 只**通知**；SCOPE 在协调下 `PROCEED`。**超时硬收尾 ✅**：warn → 硬 TIMEOUT（禁新 LLM/工具调用入口）→ 宽限一轮交卷 → 超宽限经既有 `cancel_ids` 强制取消并如实标注；嵌套子团队（无协调 session）接同一 `timeout_hard` 链路。**墙钟只计编排/空转**：LLM 调用在飞期间暂停倒计时（`mark_llm_inflight`），避免慢上游单次调用被误判 `worker_timeout`；wind_down 软着陆不变。**force_finalize 绝对墙钟**：硬顶/到顶后的收尾 LLM 流在 ReAct 轮外、inflight 又冻结活跃超时，曾可无限卡死（真实 trace：worker 僵尸 ~5min 等 CEO 手动取消）——收尾流单独套 `asyncio.timeout`（`engine_force_finalize_wall_seconds`，默认 60s），超时走既有 salvage 回落已有交付，不给 inflight 语义开特例。仅曾通知且有真缩水证据（进过 wind-down / 强制取消 / degraded handoff）才记 `worker_timeout` gap。交付缺口一等化：软放行 / 超时缩水 / 部分失败在 `RunState.delivery_gaps`、`run_completed.gaps`、`delivery_status`、CEO 工具 meta 四处显式带清单（不新增终态枚举）。检索预算：contract 返工补发切片；耗尽提前进入收尾窗。**协调取消**投终态，不投假 `ALL_COMPLETED`。产品语义见 [`编排器与CEO主Agent.md` §协调模式](/docs/03-AI核心/编排器与CEO主Agent.md)。→ 见代码: `runtime/coordination/`、`runtime/runs/timeout_hard.py`

**用户插话 ✅**：协调中新消息必唤醒 CEO；相关入图、无关转排队。附件到达即落盘，简报只带元数据。→ 见代码: `runtime/coordination/`

### 收敛治理（LoopController）

所有「循环要不要继续」的判断统一收敛到 LoopController。→ 见代码: `loop_controller.py`。

| 机制 | 阈值 | 行为 |
|------|------|------|
| 重复调用检测 | 相同签名连续 3 轮（滑窗） | ✅ 锚定事实的 `NUDGE` 反思；再次触发则 `FINALIZE` 强制无工具收口 |
| A-B-A-B 交替 | 两动作振荡连续 3 轮 | ✅ 同上两段式干预 |

### 用户级重试失败项（retry-failed）✅ 已落地

**意图分离**：`regenerate` = 推翻重来（删消息后整回合重跑）；`retry-failed` = 补救失败（复用已成功 worker，只补跑失败节点）。与 `resume`（checkpoint 续跑）共用 `seed_completed` 底层，但语义不同——resume 从挂起点之后全部重跑，retry-failed 只重跑当时仍为 `failed` 的节点。

**关键决策**：消费 seed 时按 **raw 尾缀**重映射（本回合 `delegate` 铸新前缀，旧 key 否则永不命中）——「跳过已成功」只对 DAG 具名 id 批生效，纯并行 flat 批全量重跑（数字位置号跨回合会漂）。重映射只在 delegate 侧，`WaveScheduler` 匹配语义不变。retry-failed 已删旧 journal，故须**补发** seeded 完成态呈现（`resume` / `append` 保留原 journal 不需此步）。→ 见代码: `runtime/delegate/retry_remap.py`

> ⏳ **后续**：retry-failed 是否应开新 turn 的对外语义纠正（本次仅内部投影去重，行为不变）。

**节点自动重试**（第一层防线）：DAG 节点默认 `RunPolicy(on_failure="retry", max_retries=1, retry_delay_ms=2000)`（`runs/constants.py` / `builder.py::_dag_policy`）；调度器内部静默退避重试，用尽仍失败才 `run_failed` 上报用户，并级联跳过未启动下游（见 §一 · 失败与取消）。

**确定性失败区分** ✅：`retryable=False` 跳过盲目重跑并记审计；用户可「接受此结果」。→ 见代码: `runs/wave.py`

**契约（决策层）**：

- **客户端断连 ≠ 取消**；**显式停止 = 取消**且用户停止 ≠ orphan（同步 release）；**graceful lifespan 关停 = 同款抢救收口**（打断在跑回合、落盘已有产出、`turn.interrupt_closed`、显式 release lease；超时强杀仍 release，不走 orphan）；仅真硬杀 / 崩溃标 `orphaned` 交 sweeper。
- **持久化独立于连接**；断连后仍完整落库可重放。
- **重连即回放 + live tail**：有 `Last-Event-ID` 时 journal 原序交织 DURABLE 与 `process_*`；无在飞 → 204。→ 见代码: `runtime/events/attach_replay.py`
- **硬杀韧性**：进程内 registry 非真相；真相在 `turn_leases`；孤儿租约先 orphan 热路交互再 `recover_turn` / salvage。⏳ 跨进程 Redis 租约、写类幂等键、retry-failed 对外语义纠正。→ 见代码: `runtime/leases/`

### 暂停与恢复（回合级落盘续跑）

> **设计不变量**：不引入 `RunPhase.PAUSED` 第三终态——结构化挂起暂停的是**整个回合**（CEO loop + delegate 子 DAG），而非单个 Run 节点；改用**回合级**落盘（`paused_turns` 一行 = 一个挂起回合），Run 模型零改动。
>
> **Resume = 同一回合续写（身份不变量）**：`POST …/resume` **不**开新 turn——`message_id`（= `turn_id`）、`execution_id`（取自 journal 末张 `run_plan`）、journal 游标权威源（DB `max_seq+1`）三者在 pause→resume 间不变。前端投影键同钉 `serverMessageId`（live）/ 消息 `id`（reload 已是 server id）；**禁止**「删暂停气泡 + 新建气泡 + remount 协作图」——续跑只把同一条助手消息翻回流式。否决「resume 伪装成新回合」与「client UUID 当执行槽键」——二者会反复制造 remount / UniqueViolation / 图丢帧类补丁。

**挂起即收口（②）**：到达 `plan_review` / `ask_user` / `team_preview` 检查点的回合在 `await` **之前**把整帧（`TurnSuspension`，以 `kind` 判别）落到 `paused_turns`，**落帧成功即收口终止**回合（`SUSPEND→PAUSED`、进程内 resolve Future 永不 park），所有续跑——含同会话——统一走单一冷路 `POST …/resume`，把冷热双态在检查点处塌缩为一条冷路。**窄兜底已删除（D11 ✅ · 三 kind 一致）**：原「帧没存住时退到后端限时挂起、超时自动继续」是无人能答的假等待，已删。落帧失败分两类：**运行态失败**（saver 已接线但保存抛错，如 DB / 磁盘故障）⇒ 三 kind 一律**显式报错终止回合**（`SuspensionPersistError` 上抛，不许静默放行烧钱；sidecar 本机帧 saver 同姿态——失败抛错，绝不「假 saved」）；**配置态不可用**（无 saver / 嵌套 depth>0 / 无 transcript——非生产场景）⇒ `ask_user` 如实报错、`plan_review` / `team_preview` 跳过挂起放行（`persist_unavailable`）。→ 见代码：`runtime/suspension_capture.py`。

- **持久缝**：帧只存 resume 控制元信息；窗口/已完成 worker 经 `TurnState.from_journal` 投影；显示态走 `turn_paused`（§8.3）。pause 后 journal 硬边界：落帧后不再为收口噪声追加 DURABLE；resume `initial_seq` 只认 DB `max_seq+1`。
- **恢复路径**：peek → 不 cancel 的 drain（仍在跑 ⇒ 409）→ settlement 先落库（D8）→ claim → `recover_turn`。claim 后解析失败 ⇒ 帧写回 + 5xx（禁吞成 404）。→ 见代码: `runtime/suspension_capture.py`
- **续跑与同会话并发（D9）**：resume **不得 cancel** 在跑新回合（已废除 claim 后无差别 `stop_and_drain`）；仅有限 drain，超时仍 live ⇒ 409 帧保留。cancel 版仅 `/stop` / regenerate / retry。→ 见代码: `runtime/turn_runs.py`
- **计费 / TTL / 读投影**：整回合一次计费（禁双算）；paused 7 天 idle 清；写侧 `running+paused`、读侧水合为已停态（禁误当仍在生成）。显式停止可落「未完成」消息；纯断连不触发。
- ⏳ 余项：跨进程 Redis 租约；写类幂等键；retry-failed 对外语义；治理强制层（[`远期规划 §2.3`](/docs/06-规划/远期规划.md)）。

> **⏳**：跨进程挂起（Redis BLPOP）/ Redis 租约与事件总线；写类工具幂等键；retry-failed 对外语义纠正；`frame` 再瘦 / 大正文卸 `ArtifactStore`。（结构化 `RoundOutcome`/`LoopDirective` 已落地，见 §四；sidecar 本地流中耐久见 [双模式工作区 §10.3 D6](/docs/02-架构/双模式工作区.md)。）
>
> → 见代码：`runtime/journal/`、`runtime/events/stream_checkpointer.py`、`runtime/events/attach_replay.py`、`runtime/turn_state.py`、`runtime/recover.py`、`runtime/leases/`、`runtime/interaction.py`、`runtime/facts.py`。

> 运行时收敛在三个一等模型上。每个模型把一族重复子系统坍缩成单一形状。

### 8.1 三模型总览

| 模型 | 职责 | 解决的问题 |
|------|------|-----------|
| **Interaction** | 唯一挂起原语：server 停下等 client 回值 | 统一审批/ask_user/本地工具/计划评审/阻塞式升级/逐轮辩论六套同构 BLPOP |
| **Turn Journal** | 唯一回合事实源：append-only 事实流 | 消除「回合无事实源」导致的历史回放/快照/消息完整性补丁族 |
| **Run** | 唯一执行单元：一棵 Run 树 | 统一委派/DAG/编排/路由四套并存的编排子系统 |

依赖关系：Interaction 最小独立；Journal 是 Run 的地基（事实留痕在 journal）；Run 落在两者之上。

### 8.2 Interaction（统一挂起原语 + 统一生命周期）

统一挂起原语收编审批 / `ask_user`（语义见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)）/ 本地工具 / `plan_review` / `team_preview` / 委派级授权 / 阻塞式升级 / 逐轮辩论 / **阶段推进卡**（`stage_card`，幕间衔接、跨回合耐久，语义见 [`编排器 §五·阶段推进卡`](/docs/03-AI核心/编排器与CEO主Agent.md)）九 kind，热路单一 resolve 端点 `POST …/interactions/{id}`（冷路检查点走 `POST …/resume`）。→ 见代码：`runtime/interaction.py`（`InteractionRequest`，`kind ∈ approval | ask_user | client_tool | plan_review | team_preview | escalation | debate_round | delegation_authorization | stage_card`）。其中 `delegation_authorization` **半退役**：独立热路已并入 `team_preview` 开工卡（能力授权随卡合并征询），kind / SSE 事件 / resolve schema 保留用于旧 journal 回放与 conformance。

一套机制替换四套：统一等待器、统一挂起登记（`list_pending`）、统一恢复端点、统一回值端点。per-kind 差异降为策略位（durable / 键粒度 / at-rest 脱敏）。**`paused` 落盘续跑**见 §暂停与恢复；**跨进程等待**（Redis BLPOP）⏳。

**统一生命周期（提问确认交互统一重构 ✅）**：8 种「问用户」交互共享「登记 → 展示 → 答复 → 留痕 → 失效」一条生命周期；唯一保留的分叉是答复后回合怎么继续（冷恢复 vs 热唤醒——「阻塞整轮 vs 不阻塞」是本质二元，escalation 挂起时兄弟 worker 还在跑）。

- **全 kind journal 化（D3）**：`*_required` / `*_resolved` / `interaction_orphaned` 均 DURABLE；**pending 集 = journal fold**；**否决**新建 `interactions` 表。
- **失效（orphaned）语义**：四触发点（turn 终了 / sweeper 先 orphan 再重驱 / resolve 410 / regenerate·retry·stop）；**断连 ≠ 失效**。
- **不答语义（D2）**：默认无限期等待；废除静默 auto-DENY / 超时自动回落——改为卡片常驻按钮由用户显式触发。
- **同对话并发（D9）**：热挂起→409；协调→插话 SSE（``user_interjection``）；其他 in-flight→FIFO 排队 SSE（立即 ``turn_queued``，drain 后**同一连接**续流）；空闲→正常 SSE。冷 paused 可发消息；反向 resume 遇新回合→409。202 JSON（queued/delivered）已退役。→ 见代码: `runtime/turn_queue.py`
- **跨端一致（D4）**：补齐客户端，**否决**后端按客户端能力降级。

### 8.3 Turn Journal（唯一事实源）

每 turn 一条 append-only 条目流（主键 `turn_id + seq`）。→ 见代码：`runtime/journal/`、`runtime/facts.py`、`runtime/journal/writer.py`。

**关键设计抉择**：执行事实与展示事件共用**单一有序日志**（`TurnFactLog`：sink 转发 + 引擎直记交织），否决「执行流与展示流分家再归并」——两流须同发生序才能正确 fold 窗口/快照。

**持久化模型（Append-on-Emit）✅**：每条 fact 在 **SSE 送达前先落盘**（`TurnJournalWriter` contextvar 绑定每个 turn），否决「pause 时 batch snapshot」——前端能看到的一切 DB 里必然已有。数据流：`record_turn_fact → DB append (barrier) → SSE emit`（barrier Future 回流 seq → SSE `id:`）。**并发模型**：writer 是**单消费者有序 write-behind**（入队即定 emit 序），同刻只占 1 条 DB 连接——否决「每条 fact 扇出任务+连接」（宽并行委派会打爆连接池）。**turn owner 在每条回合路径终了（新回合 / resume / pause）都必须在 reset writer 前 `await flush()`** drain 队列尾巴（否则在飞写任务泄漏连接）；pause 再额外写控制帧（journal 早已逐条在 DB），消除「frame 在 journal 缺」的中间态。删消息时联动清理 `paused_turns`（防 orphan frame）。

**process / run_process 车道渐进持久化 ✅**：凡 live 时间线可见的步骤，须在对用户可见前写入 journal；运行中刷新与终态重载只 fold journal。落盘粒度 = 语义边界步（非 per-token）；Finalize 只补未闭合尾；写序保证 process_* 先于触发它的 DURABLE 入队。→ 见代码: `runtime/events/process_persist.py`

**流式耐久投影（`turn_stream_state`）✅**：token 增量不进 journal；累积文本快照经 `StreamCheckpointer` UPSERT。**纯散文回合边界（已拍板）**：无 process 车道的回合不扩展 `process_*`，`messages.content` 即答案。→ 见代码: `runtime/events/stream_checkpointer.py`

**seq 权威在 DB · 双模式（D7 ✅）**：live 模式 `seq=None` ⇒ DB 原子分配；merge 模式保留显式 seq 幂等。**禁止**无锁 MAX+1 吞冲突；**否决**主键改 ULID。

**settlement 事实必达（D8 ✅）**：settlement 走同一 write-behind 插队 + await；冷路 settlement 先于 claim。**决策：dedupe 键须携带完整事件 kind**。→ 见代码: `runtime/journal/pending_interactions.py`

**回合态暂停快照（`turn_paused`）✅**：可恢复回合态组装成 `turn_paused` fact；`process` 已退役双写。**规则：新增任何回合内累积态，必须同时声明挂起归宿与再水化点。**→ 见代码: `runtime/turn_paused_capture.py`

**投影不变量表**：

| 消费面 | 来源 | 现状 |
|--------|------|------|
| SSE 流 | 引擎实时 emit（流式增量不入 journal；DB barrier 在 emit 前；DURABLE 帧带 `id:`） | ✅ |
| 执行级事实记录 | `react_loop` 经 `record_turn_fact` 直写单一有序日志 + DB | ✅ |
| 持久化消息行 | journal 投影器 `runs_from_entries` + 在飞 overlay（`turn_stream_state`） | ✅ |
| 流中部分态 | `turn_stream_state` UPSERT 快照（终态后删除） | ✅ |
| 暂停快照 / resume / 崩溃恢复 | `turn_journal` + `TurnState.from_journal` → `recover_turn`；显示/控制态经 `turn_paused` 单点再水化；无 DAG → stream_state salvage | ✅ |
| 跨轮历史回放 | 文本 + interaction 答案投影 | ⏳ |
| LLM 窗口 | `window_from_journal` | ✅ |

**审计投影层 ✅**：`agent_audit_events`（多 Agent 协作追溯）是 journal + 运行时钩子的**下游只读投影**——`AuditRecorder` 先 journal 后审计偏序采集、`causal` 复用 `depends_on`/`parent_run_id` 重建 parent/depends_on/inject 因果边，**非第二事实源**。治理面（受众 / schema / 因果 / 双 API + 文件反查 / 留存 / 被否决取舍）→ [`安全权限与治理.md §八·Agent 行为审计`](/docs/05-平台与运维/安全权限与治理.md)；→ 见代码：`runtime/audit/`。

### 8.4 Run（唯一执行单元）

执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定：

- 单 Agent = 单节点
- `fan_out` = 单波 + captain 汇聚
- `pipeline` = 线性链 + captain 汇聚
- `adaptive` = 空计划 + captain 动态追加
- 单次 delegate = 追加一个节点
- best-of-N 择优 = 某节点 `candidates>1`（`RunPolicy` 策略位，非独立 kind）
- 辩论/审查 = 主持人（Moderator）驱动的逐轮交锋（✅ 已落地，见 [`辩论编排设计.md`](/docs/03-AI核心/辩论编排设计.md)）：主持人是 CEO 的 `debate` 工具内的确定性循环（非 LLM 委派角色）、辩手为 `depth+2` 叶子，底层仍是普通 AGENT DAG（**非独立 kind / 无 arena 子系统**），轮次由主持人逐轮判收敛自停（取代旧的 CEO 手搓静态跨轮 `depends_on`）

> **决策（CEO = 根 Run 节点 ✅）**：CEO chat loop 即本回合 `CAPTAIN` 根 Run；content/reasoning 走气泡级 `content_delta`/`reasoning_delta`（非 run 级）；captain 一次定价、落真实台账行。**否决**旧的 `synthesis` 零成本伪 run。

> **决策（嵌套委派）**：`depth < MAX_DELEGATION_DEPTH` 的 worker 默认获 `delegate`+`replan`（委派默认开、无 opt-in 开关，见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)）。**硬上限 `depth ≤ 2`**：depth=2 sub-worker 永不获 `delegate`；单 lead 扇出上限 `MAX_WORKER_SUBDELEGATIONS = 4`。

> **决策（可恢复运行 `RunSession`）✅**：一次 worker run 执行后不丢弃，保留完整 transcript = `RunSpec` / `RunState` 的**可恢复延伸**；CEO 经 `delegate` 带 `continue_from_run_id` 在保留 transcript 上追加指令、重跑 `react_loop` 即「续干」（改稿或新任务；同轮 / 跨轮 / 跨进程留人，双 miss 明确拒绝回落冷委派）。统一收编自动返工 / CEO 续派 / redirect 热修 / 辩论续轮四条接缝。详见 [`多轮编排与同人续派.md`](/docs/03-AI核心/多轮编排与同人续派.md)。

### 8.5 引擎纯化

三条去特判手段：

1. **工具效应模型**：`ToolResult(text, effect)`，`effect ∈ Continue | Handoff | Interact`。引擎只解释效应，`delegate`/`ask_user` 不再是特殊名字
2. **显式 ToolContext**：工具签名携 context（user/conv/turn 等），消灭 `set_runtime_context` 全局大杂烩
3. **去工具名特判**：引擎按能力位（`has_delegation_tool` 等）而非工具名判断行为

### 8.6 端口契约（宿主注入）

引擎面向宿主的 10 项端口（本地/云端同码、宿主注入）；契约在代码里镜像为 `runtime/ports.py`（**ClientRequestBridge / Journal / ConversationStore 已落地**、EventSink 已是端口，余项仍为其具体实现、待 Sidecar 取用时再 Protocol 化）：

| 端口 | 定位 |
|------|------|
| Journal ✅ | 引擎唯一持久化出口；`turn_journal` 表 + `TurnJournalRepository`，`runs` 读取时投影自它（§8.3） |
| EventSink ✅ | 渲染流出口（流式增量 + 离散事实实时投影）；`runtime/events/`，`ports.py` 再导出 |
| InferenceGateway | LLM 调用 |
| ArtifactStore | 归档/寻回 |
| PauseSignal | 暂停信号（Redis flag） |
| ClientRequestBridge ✅ | 统一挂起原语（`runtime/interaction.py`；审批 / ask_user / 本地工具 / **plan_review（2a）** / escalation / debate_round） |
| ConversationStore ✅ | 回合持久化 driver（`begin_turn` / `checkpoint` / `append_journal` / `finalize` / `salvage`）；`CloudStore` 直落 PG、sidecar `OutboxStore` 落本机 outbox，本地经 `/local-turns` 走 `finalize(mode=local)` 合并落库（链路 + 合并契约见 [双模式 §10.3](/docs/02-架构/双模式工作区.md)） |
| BillingSink | 计费事实投影 |
| DelegationTransport | 跨进程子树传输 |
| SnapshotStore | 已被 Journal 吸收 |

### 8.7 一轮一网关（Gateway 传播原则）

当用户自带 LLM 凭据时，整棵多 Agent 委派树必须在**同一把网关**下运行，避免 split-brain（captain 跑用户 key，委派出去的子 Agent 回落平台 key）。

**规则**：在 Turn 最早阶段（工具装配之前）一次性解析 `effective_gateway`，随 Run 上下文贯穿整棵执行树。`InferenceGateway` 端口接收的凭据由此确定——直答、团队编排、恢复各路径读同一把。

此原则与凭据来源开关无关（无论平台供还是用户供），是执行语义的不变量。
