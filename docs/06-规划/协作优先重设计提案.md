## 〇、已拍板前提（2026-07-14 产品负责人）

> **协作是第一性、默认多 Agent。**协作不是可选优化，是产品的存在价值本身——如果大多数任务都路由到单 worker，产品与「单 Agent + 好看的可视化」无异。

本提案所有设计从这条前提正向推导。它推翻/动摇现有文档中的若干已落地决策，见 §一.3 冲突清单。

## 一、背景与证据

### 1.1 机制不缺，缺的是「发生」

协作机制在设计文档里相当完备（DAG 委派、嵌套 lead、便签墙、`escalate` 三档、`handoff`、波边界 `replan`、辩论主持人、检查点），但全量开发日志统计（119 次 `delegate`，含合成/评测流量，**无真实用户数据**，仅作方向参考）显示：

| 机制 | 触发量 | 解读 |
|---|---|---|
| `delegate` 派团 | 119 次（46 次单 worker） | 派单是常态 |
| playbook | 8 次，全部 `research_report` | 另两个模板 0 次；模板坍缩 |
| `replan` 波边界纠偏 | 1 次 | 「边干边调整计划」不发生 |
| worker `escalate` | 7 次 | 「干活中喊人」不发生 |
| 便签墙贴 / 读 | 32 / 43 次 | 零星，未成日常 |
| 辩论 | 39 场 | **唯一真正跑起来的可见协作** |

### 1.2 三层根因

1. **规划层：团队形状不来自任务结构。**「4 家公司 × 4 维度」的任务天然形状是按公司分组、组内拆维度、尾部横向对比；提示词却把模型漏斗进通用流水线模板（skill 散文 +「是就直接套」姿态 + schema 广告位三处合力）。换个主题形状一模一样。
2. **执行层：协作被设计成「自觉行为」，而模型不自觉。**便签、升级、返工全是 opt-in、靠散文期望快模型主动触发。项目已有实证：委派软护栏 A/B 测过「被模型无视且净负」后移除。**反例是辩论**——它的互动由 Moderator 确定性循环结构驱动，不靠自觉，也是唯一跑起来的协作。这是「协作长在结构里」路线可行的内部证明。
3. **度量层：没有「协作质量」的定义与评测。**好协作长什么样无可检验标准，优化全靠体感，陷入打补丁循环。

## 二、设计原则（提案，待批）

- **P0 协作优先（已拍板）**：实质任务默认组队。组队门槛线草案：任务具有**可分解结构**（多对象 / 多角度 / 多阶段 / 多部件）**或需要把关的质量面**（成篇、构建、决策、既有材料的审查）即组队；纯机械单步（转格式、改一句话）与闲聊/单点事实留单 worker / 直答。✅ 已拍板：连接词取「或」（产品审计的「且」方案否决——协作第一性优先，控税交给三档形状的轻档）
- **P1 结构优先规划**：团队形状从任务的自然结构推导（并列对象？流水线阶段？对抗视角？发散方向？部件拼装？既有材料多透镜？），规划层学的是**形状词汇表 + 组合规则**（§五），不是成品模板。自检判据：换个主题，形状还一模一样吗？
- **P2 协作长在结构里**：重要的互动（对齐、审查、返工、冲突消解）必须是计划里的**节点、边、共享面**，不是提示词散文里的期望。辩论是既有证明案例。
- **P3 协调税分档支付**：每个原型给轻/中/重三档形状（§三通则），规划层按任务规模选档。协作优先 ≠ 到处开满配——税要花在该原型的硬增益上。
- **P4 协作质量可评测**：**主指标 = 相对单 Agent 的交付质量（同任务单 Agent 基线盲评对比）+ 形状匹配度**；互动发生率只作辅指标且**只认「该发生处的发生」**——否则评测会奖励协作剧场（详见 §六 阶段 1）。

## 三、剧本通则（v2 新增，适用于全部原型）

1. **一条硬增益**：每原型只钉一条硬增益作为组队正当性来源（并行提速、便签互贴、人设发散等一律标次要，不得作为评测优化目标）。
2. **每任务恰好一个主拍板**：开工确认 / 提纲 / 挑选 / 风险确认 **四选一**；其余人介入降为例外升级（只有影响范围/预算/不可逆时才 `ask_user`）。「中途重大动态默认问用户」类设计一律删除——团队内消化。卡片合并/跳过规则阶段 3 随 B1/B2 重理。
3. **三档形状（降档条件）**：每原型写明轻/中/重三档与选档判据；默认中档，轻档保底、重档需任务规模或用户点名支撑。
4. **失败退路**：审查/验证/修订环到限（≤2 轮）仍不达标 → 不空转、不假装收工，向用户交代缺口与建议（对齐既有 4a 完工判定）。
5. **多轮接续**：剧本不止首轮——用户回来改需求/改稿时，默认带现场续派回原作者（同人续派机制已就绪），不重开全新团队。
6. **评测断言**：每原型的「理想形状 + 该发生的互动」即阶段 1 合成场景的断言来源，写剧本时即写断言。

## 四、七个任务原型的理想协作剧本

> 模板：例 → 触发特征 → **硬增益**（组队正当性）→ 形状三档 → 中途互动 → 主拍板 → 收尾 → 现状差距。（✅ v2 剧本随 §七 十项决策于 2026-07-14 一并定稿）

### 原型 1：多对象研究对比（宽度型）

- **例**：「分析 OpenAI / Google / Anthropic / Meta」「对比 5 款车 / 3 个城市」。触发特征：多个并列实体 × 多个维度，要求横向可比。
- **硬增益**：**口径一致性**——对比报告最大质量杀手是各实体口径漂移（统计时间、货币单位、来源可信度），用共享面播种统一口径 + 汇总前对账治它；单 Agent 长对比同样会前后不一。次要增益：并行提速、每实体不挤上下文。
- **形状三档**：轻 = 2~3 实体浅比，单 worker 直接写。**中（默认）= 每实体一名调研员（扁平）+ 横向对比员（`depends_on` 全部）**，`coordination=wall` + CEO `seed_notes` 播种口径。重 = 实体多且用户点名深覆盖时，每实体一个 lead（内拆维度 ≤4）+ 对比员；注意扁平「4 实体×4 维度」=16 节点超顶层上限 10，深覆盖**必须**走分组，且各 lead 在子批自播口径（B5）、组内升级直挂用户（B4）。
- **中途互动**：口径级决定贴 `decision` 便签；数据缺口 `escalate kind=dep` → 波边界 `replan(add)` 补定向调研。~~重大动态默认 ask_user~~（v2 删除：易假紧急、烦用户；仅当影响范围/预算时才升级）。
- **主拍板**：开工确认（实体清单、维度、口径预设）。
- **收尾**：CEO 对账口径一致性与实体覆盖均衡（4b），综述差异亮点，指引看对比表。
- **现状差距**：`research_report` playbook 抢走这类任务（形状错）；wall 缺省关；分组形状不被自发使用。

### 原型 2：深度成篇写作（深度型）

- **例**：「写一篇 XX 论文 / 深度报告 / 长文」（单主题深挖）。触发特征：单对象、成篇、证据密集。
- **硬增益**：**独立审查环**——审查者 ≠ 作者（自审是结构性盲区）+ 结构化问题清单 + 有界修订（≤2 轮）。「结构跟着证据走 + 提纲把关」是既有产品级增益，保留。次要增益：多角度并行调研（真增益来自强制不同信息源/问题清单，不是人多）。
- **形状三档**（2026-07-14 拍板改**审计后派**：独立审计不再预排在首张 DAG，改为成品落盘后 CEO 单独后派——冷眼进场独立性最彻底（B6 下独立性=上下文隔离）、审的对象=用户将拿到的落盘成品、环每步都是显式委派可计数可拦截；**系统只软提醒、绝不代派**）：轻 = 撰稿落盘 + 后派 1 审计员（短文，环 ≤1 轮）。**中（默认）= 角度调研×N → 提纲（主拍板）→ 撰稿（成品落盘）→ 后派独立审计（冷启动读成品全文，产出结构化问题清单）→ 修订环**（续派唤回原作者修订 → 审计员复核，≤2 轮）。重 = 审计升 2-3 透镜分工（事实核查/逻辑/受众），问题清单按风险分级合并。
- **中途互动**：调研员关键发现贴便签（次要，不作质量证明）；审校与作者真冲突 → CEO 仲裁（罕见才有价值）。
- **主拍板**：提纲检查点。~~已知结构缺口（B1）~~ ✅ 阶段 3 第 3 件已解：含把关节点的批强制走经典阻塞路径，durable 提纲卡（continue/adjust/stop + 批注引导下游）如期弹出。
- **约束写实**：修订环由 CEO 多轮 `delegate` 驱动（初派 + 1~2 次续派，0 次 replan 也可）；作者链唤回上限 3；审查独立性 BYOK 下仅角色级（B6）。
- **收尾**：CEO 报告审校发现了什么、修掉了什么（让用户看见质量环真跑过），交付成品。
- **现状差距**：现有骨架方向正确，但审校是终点不是环；CEO 不自发用续派做修订环。

### 原型 3：构建类交付（接口协作型）

- **例**：「做个网站 / 小工具 / 脚本」。触发特征：产出可运行物。
- **硬增益**：**真跑通**——独立验证者 + `code_verified` 客观验收（协作里少数可证伪的增益）。次要增益：模块并行、接口契约对齐（中大活才真）。
- **形状三档**：**轻（默认小活）= 实现者 + 独立验证者双人**（✅ 双人底线已拍板）。中 = 按活的自然模块拆分 + `wall` 接口契约广播 + 独立集成验证。重 = 接口定稿节点/lead + 前端 ∥ 后端 ∥ 测试。**前后端拆分是重档特例，不是默认队形**（产品面向大众，默认英雄场景不锁死在开发者任务上）。
- **中途互动**：接口/字段决定贴 `decision` 便签；测试挂 → 定向续派原作者修复（≤2 轮）；缺依赖 `escalate kind=dep`。
- **主拍板**：开工卡（含能力授权——安全刚需，保留；不再叠第三张风格问卷）。
- **收尾**：CEO 汇报「跑通了什么、怎么验证的」，附启动方式。
- **现状差距**：`build_feature` playbook 0 次使用；验证者独立无 enforce（criteria 未强制验证 run ≠ 实现 run）。

### 原型 4：开放决策权衡（对抗型）

- **例**：「两个 offer 选哪个」「该不该 all-in 某方向」。触发特征：无标准答案、多立场张力、用户要「想清楚」。
- **硬增益**：**结构驱动的真对抗**（Moderator 循环压力测试论点）——现状最成熟，也是「协作长在结构里」的内部证明。
- **形状**：沿用辩论编排（多立场辩手 → 逐轮交锋 → 修订对射 → 收敛 → 简报 + 用户拍板）。
- **补强**：① 拍板后衔接执行团队（转原型 2/3/7）——**缓做**（✅ 已拍板；连续性缺口而非协作形状缺口）；② **局部辩论 = 冲突消解的备用词汇**（其他原型中两 worker 结论真冲突时 CEO 可开小型辩论），**禁止**「默认冲突即开辩」——成本炸弹 + 稀释辩论招牌。
- **主拍板**：终局拍板（辩论已有）。
- **现状差距**：小。多模型辩手在远期（对抗独立性同为角色级，B6）。

### 原型 5：创意多方案（发散挑选型）

- **例**：「起名 / slogan / 海报方向 / 文案风格」。触发特征：审美主观、答案发散、用户要可挑选的差异化选项。
- **硬增益**：**人挑选**——多风格方案墙 + 用户挑选 + 中选作者带现场续派深化；「领导者做选择」是本原型的产品核。次要增益：多人设并行发散（同底座模型有风格坍缩风险，靠人设差异化播种约束 + 评测盯方案区分度）；交叉互评**降为轻量结构**（结构化短评、只挑受众错配/硬伤，防互相吹捧——不作质量证明）。
- **形状三档**：轻 = 3 方案并行、无互评、直接挑。**中（默认）= N 风格并行（N≤5）→ 轻量交叉互评波 → 方案墙挑选（主拍板）→ 中选深化**。重 = 挑选后多轮深化迭代。注意 N 风格 + N 互评双波节点数逼近顶层上限 10，N≥6 必分批。
- **主拍板**：挑选。✅ 阶段 3 第 3 件已落地「方案挑选卡」：`ask_user` 带 `card="proposal_pick"`（复用 choice 单选 + recommended + selected 回流，恰 1 问、选项 2–6；不新增交互 kind，移动端自然降级为普通选择卡）。
- **收尾**：CEO 报告各方案定位与互评共识，深化后交付。
- **现状差距**：互评波无结构承载；挑选卡不存在；挑选→深化靠 CEO 自觉拼第二轮。

### 原型 6：审查诊断（评估型）【v2 新增】

- **例**：「帮我看看这份合同有什么坑」「审下我的简历 / 方案 / 对外回复」。触发特征：用户带来**既有材料**，要「找坑、分级风险、可行动建议」，不是再写一篇。
- **硬增益**：**独立多透镜诊断**——条款/事实/风险/受众等 N 个透镜并行审 + 风险分级汇总；自审盲区是单 Agent 的结构性缺陷。法律垂直（`legal_answer_brief` 对方律师作战室）已是雏形，本原型把它抽象成平台通用形状——平台与垂直不再脱节。
- **形状三档**：轻 = 单审查员 + 红队复核双人。**中（默认）= N 透镜并行诊断 → 风险分级汇总员**。重 = + 对方视角红队（对抗压测，衔接局部辩论词汇）。
- **中途互动**：透镜间对同一条款/段落的发现贴便签防重复；发现按严重度分级汇总，**不中途打断用户**。
- **主拍板**：风险确认卡（哪些要改 / 要深究）→ 用户勾选后可衔接定向修订（转原型 2 修订环）。✅ 阶段 3 第 3 件已落地：`ask_user` 带 `card="risk_ack"`（choice 多选、选项 1–10、label 以严重度开头约定）。
- **收尾**：分级风险清单 + 每条的证据位置与建议动作。
- **现状差距**：无平台级形状（法律是 opt-in 垂直特例）；~~风险确认卡交互不存在~~（已落地，见上）。

### 原型 7：组合方案规划（拼装一致性型）【v2 新增】

- **例**：「自媒体启动方案」「旅行计划 / 婚礼筹备 / 开业筹备」。触发特征：多部件交付（定位/选题/变现；行程/住宿/预算）且**部件间必须互相一致**，用户要可执行方案不是散文。
- **硬增益**：**约束共享面 + 部件一致性对账**——预算上限/日期/人设红线播种为共享约束（wall + seed），尾部一致性对账节点专查部件接缝（行程超预算、选题与定位打架）；这正是单 Agent 长方案最容易前后打架的地方。次要增益：部件并行提速。
- **形状三档**：轻 = 单 worker 写全案 + 一名对账审查。**中（默认）= 约束播种 → 部件并行起草 → 一致性对账员 → 定向修订（≤2 轮）→ 定稿**。重 = 部件 lead 分组（大型筹备）。
- **中途互动**：部件间共享决定贴 `decision` 便签（「总预算 1.2 万、日均 xx」）；对账员发现冲突 → 定向续派修订。
- **主拍板**：约束确认（开工卡）**或**方案墙挑选，**二选一不叠加**——双检查点会把旅行计划做成项目管理软件。
- **收尾**：CEO 报告部件间一致性对账结果 + 方案总览。
- **现状差距**：这类请求现被漏斗进 `research_report` 或平铺扇出；一致性对账无结构承载。与原型 3 同族（部件 + 接缝 + 集成验证），验收从「真跑通」换成「语义一致性」。

### 次优先任务家族（不进主集，词汇可组合表达）

- **批量内容生产线**（一周 7 条脚本 / 系列邮件）= 口径定稿 + 并行产稿 + 抽检审校；**学习辅导/备考**（30 天计划）= 摸底 → 计划 → 练习反馈环；**数据分析** = 角度扇出 + 流水线。阶段 2 规划层用组合规则覆盖，暂不单列原型。（✅ 已认可）

### 阶段 3 第 1 件：组队门槛软闸门 ✅（2026-07-14；`long_content` 分支 2026-07-17 撤）

引擎层 captain-only、每 run 至多一次（`engine.team_gate_nudge`）。**现状只保留**调查工具累计 ≥3 次仍欲继续 → 注入门槛复核提醒（信号质量高；阈值曾为 2，后试调至 3）。**软闸门**：给归类理由仍可自主直答；已 delegate 永不触发；worker 不受影响。
