## 一、架构演进（本地引擎已落地，剩离线 LLM / 跨进程 / 精确续局三条远期触发项）

> **已落地（as-built 见 [`../02-架构/双模式工作区.md §十`](/docs/02-架构/双模式工作区.md)）**：sidecar 本地引擎——桌面 spawn `python -m agentcore.sidecar` 跑**同一 `run_chat_pipeline`**、stdio JSON-RPC、工作区直连本地盘；LLM 经云代理权威计费（Slice 4a，平台 key 不下放，岔路 B）+ 回合云端回写（`local-turns` 幂等）+ 结构化挂起本机帧（durable pause/resume）+ 内置 Python 打包（方案 B）+ `Journal` 端口 / 执行级事实。绑本机本地文件夹的对话走 sidecar，开关「本地引擎」已**默认开**、可关闭（启动失败自动降级回云端兜底 + 首次走 sidecar 前探活预检、偏好三态存储）。
>
> **驱动力（已识别）**：同一用户兼做「改本地真实仓」与「泛知识工作」，本地交互不能长期二等（「云端引擎遥控桌面」单通道在速度 / 并行 / 离线均受限）；beta 维持「默认云 + 打开文件夹经 `WorkspaceChannel` 实时改本地真文件」作兜底。
>
> **来源**：原 `02-架构/技术架构与基础设施.md §六`（曾名《架构演进提案》）。其中「客户端工具执行 + 本地优先 folder」（引擎在云、文件 op 遥控桌面）与「引擎本体搬到本地」（sidecar）均已落地、迁入 [`双模式工作区.md`](/docs/02-架构/双模式工作区.md)（§四 / §十）；其余借鉴项（统一 Run / WaveScheduler / `delegate` / Turn Journal / Interaction 挂起）归 [`执行引擎架构设计.md §八`](/docs/03-AI核心/执行引擎架构设计.md)。本节仅余下面三条**未落地、待触发**的演进。

### 1.1 完全离线（本地推理 + 本地消息库）

现 sidecar 是**混合态**：引擎在本地，但推理 / 持久化 / 计费仍借道云（见 [双模式工作区 §10.2/10.3](/docs/02-架构/双模式工作区.md)）。完全离线 = 把这几条也换本地实现，让整轮零云依赖：

- **本地 `InferenceGateway`**：接本地模型（Ollama / llama.cpp / LM Studio 等），不走 `/v1/inference` 云代理（复用 `LLMProvider` 抽象 + 工厂，见 §2.2）。
- **本地消息库**：sidecar 本机 SQLite 落消息，替掉云端 `local-turns` 回写（`ConversationStore` 端口本地实现）。
- **计费解耦**：离线 = 用户自有算力、不计费（本地 = free，`BillingSink` 空实现）。
- **价值**：真离线 / 隐私（数据不出机器）/ 零推理成本。
- **代价 / 就绪度**：[执行引擎 §8.6](/docs/03-AI核心/执行引擎架构设计.md) 的 10 宿主端口当前仅 3 个 Protocol 化（`EventSink` / `ClientRequestBridge` / `Journal`），其余 7 个仍具体实现——`ports.py` 明示「无第二实现时 Protocol 化 = 过早抽象」，故**按纪律留缝、不预抽**；本地模型质量 ≪ DeepSeek V4，大众定位下属 niche。
- **绑定项·JSON-RPC 云侧统一**：sidecar 桌面↔本地通道已是 JSON-RPC；本项可顺带把**云侧** SSE + HTTP（[执行引擎 §二](/docs/03-AI核心/执行引擎架构设计.md)）也统一为 JSON-RPC 运行时协议（云 / 桌面 / UI 一套代码、pause/resume/交互回值天然统一）。**但 SSE 事件契约已稳定对齐、无独立收益时重构纯亏**，故与离线绑定、离线不做则不动（**非 MCP**——MCP 仍用于 Agent↔外部工具）。
- **启动触发**：出现明确的隐私 / 企业自托管 / 真离线诉求。

### 1.2 跨进程子树分发（C2）

worker 委派现为**进程内** asyncio 子 task（`DelegationTransport` 端口仍具体实现）；跨进程 = 把委派子树分发到别的进程 / 机器（Redis durable queue + 跨进程挂起 BLPOP）。

- **价值**：多机扩容、本地内环 + 云端并行团队混合执行。
- **就绪度**：[`双模式工作区.md §五`](/docs/02-架构/双模式工作区.md) 多 worker 的锁 / 审批门 / 通道 / handoff 现为进程内态；限流已留 `RateLimiter` protocol 缝；挂起跨进程 Redis 见 [执行引擎 §暂停与恢复](/docs/03-AI核心/执行引擎架构设计.md)。
- **启动触发**：单机并行触顶 / 多副本部署 / 本地↔云混合执行成为真实诉求。

### 1.3 执行内精确续局（从中断轮次续跑）

「已决策 · 执行中断」的一键续跑现为**从决策点重跑**（[双模式工作区 §10.7](/docs/02-架构/双模式工作区.md)：辩论即 `skip_kickoff` 式重跑整场）——丢弃已跑部分进度、重复消耗该部分 LLM 成本。精确续局 = 从中断轮次继续，云 / 本地均无现成机制（moderator 非 DAG、无逐轮 checkpoint 续局能力），需为各编排原语新造执行内断点，范围大。

- **价值**：长执行（多轮辩论 / 宽扇出团队）中断后不重复烧已跑部分的成本。
- **启动触发**：真实使用中「从决策点重跑」的重复成本成为可感痛点。
- **来源**：原 06《回合恢复状态机收口提案》方案 B（提案已退役，D1–D3 as-built 迁入 [双模式工作区 §10.4/10.7](/docs/02-架构/双模式工作区.md)）。

## 二、平台能力演进（抽象已预留、第二实现待启）

> 共性：抽象接口（Protocol + 工厂）或机制扩展点在 MVP 即预留、首实现 / 首模式满足发布；第二实现 / 强制模式属**发布后**增强，出现明确驱动力才启动——与 §一 Sidecar 同范式（「抽象先行、第二实现留缝」的能力域版）。

### 2.1 真实沙箱（SandboxProvider 第二实现）

代码执行默认走受限 `SubprocessSandbox`；**gVisor 第二实现已落地并完成生产化**（2026-07-17：产物写回 copy-in/copy-out、并发/时长/内存灰度护栏、镜像内置 runsc 与文档/数据库、沙箱叠加 compose；`GVISOR_ENABLED` 默认仍关、按部署灰度开启）——执行模型与护栏权威见 [安全 §五](/docs/05-平台与运维/安全权限与治理.md)，部署面与部署后验证清单见 [部署与运维 §云端执行灰度](/docs/05-平台与运维/部署与运维.md)。**被否决**：服务端受控文档生成专用能力（「路线 B」：pptx/docx/xlsx 由服务端受控库直接生成为可下载产物）——2026-07-17 拍板不立项，云端通用执行灰度已覆盖文档生成场景，不为单一产物类型建平行能力面。本条收口**更强隔离的后续方案**：

| 方案 | 结论 |
|---|---|
| 独立小虚拟机（Firecracker） | 换带 KVM 机器后平滑升级 |
| 独立 Worker + NATS | API 永不接触 Docker；代码执行经 NATS request 转发到 worker 容器 |

- **价值**：不可信代码安全执行、多租户隔离。
- **启动触发**：gVisor 生产化（原「公测上线前必做」项）✅ 已完成；Firecracker / NATS 按扩容与隔离需求再启（灰度期真实负载 / 逃逸面评估触发）。

### 2.2 多 LLM Provider（LLMProvider 第二实现）

默认 `DeepSeekProvider`（Flash + Pro）+ **已落地的 `ProviderRouter`**（按 `provider/model` 前缀分发）；其余模型家族（海外 / 本地 / 其他厂商）经 `OpenAICompatibleProvider` 接入，`llm/factory.build_router` 据已配厂商 key 组装注册表。

- **价值**：出海与多模型选择、客户指定模型、对冲单一供应商的可用性 / 成本风险。
- **代价**：各家 API 差异（工具调用 / 思考模式 / 流式增量）需在 provider 层抹平；定价表与计费每接一家加一份。
- **就绪度**：✅ 多 provider **路由已落地**——`ProviderRouter` + `OpenAICompatibleProvider`，`build_router` 据已配厂商 key 组装（Kimi / 智谱 / 豆包 前缀，配 key 即启用；空 key 退化为「只有 DeepSeek」零行为变化），已作「真·多模型辩手」执行支点（as-built 见 [`辩论编排设计.md §7.5`](/docs/03-AI核心/辩论编排设计.md)，各厂商接入事实 / model 串约定见 [`平台LLM接入.md`](/docs/05-平台与运维/平台LLM接入.md)）。BYOK「一轮一网关」凭据传播原则已定（[执行引擎 §8.7](/docs/03-AI核心/执行引擎架构设计.md)）。**仍属远期**：本地推理网关（Ollama / llama.cpp）、**模型目录 + 各家定价表 + 前端选模型 + 计费归因**（每接一家加一份）、跨家族质量档对齐。
- **被否决**：① OpenRouter 聚合网关 → 暂不（先连国内 Kimi / 智谱 / 豆包）；但「通用 OpenAI 兼容 provider + 路由器」地基对 OpenRouter 同样适用、将来可低成本接。② 逐家官方 SDK（Anthropic / Google 非 OpenAI 格式、多把 key）→ 否；统一走「通用 OpenAI 兼容 provider」一套。
- **启动触发**：出海需要海外模型 / 客户要求指定模型 / 对冲单一供应商风险。

### 2.3 治理强制检查点层（结构化挂起的强制模式）

> **来源**：原 07 草稿《结构化挂起后端落地设计》§4.7「治理强制注入层」**已退役删除**；该蓝图 2a/2b 全落地迁入正式文档后，唯一延后项迁出至此。

结构化挂起底座（`WaveScheduler.on_checkpoint` + `InteractionRegistry` 的 `plan_review` kind + 回合级 `paused_turns` 落盘 + `POST /resume`）已全落地，**首模式 = CEO 自声明** `checkpoint_after`（CEO 自愿在高危 step 后标记，用户 continue/adjust/stop，软挂起 timeout=continue 放行，已满足发布）；**第二模式 = 治理策略强制**：检查点由策略强制注入（非 CEO 自愿声明）、声明即必停（不可被 CEO / 用户跳过）、挂起点可审计留痕、超时取 `halt`（而非软挂起的 `continue`）。

- **价值**：合规 / 企业治理场景的「保证闸门」——某些高危 / 不可逆步骤必须由人确认，不依赖 CEO 自觉；审计留痕满足审查要求。
- **代价**：调度器 / 计费 / 事件层需区分「自声明 vs 强制」两类挂起；timeout 语义按类分流（软 = continue、强制 = halt）；强制注入规则的策略面与配置。
- **就绪度**：机制底座 + 首模式（CEO 自声明）已全落地（见 [`../03-AI核心/执行引擎架构设计.md` §暂停与恢复](/docs/03-AI核心/执行引擎架构设计.md)）；仅缺「强制注入 + 必停 + halt 超时 + 审计」这层策略。
- **启动触发**：出现明确的合规 / 企业治理需求（某类客户或审查要求强制人工闸门）。

### 2.5 交付前核验·重层审查（独立审查 worker，高风险触发）

> **来源**：原 07《交付前核验设计》（2026-06 实测复盘：宣传官网 / 建设工程法律实务会话）。轻层 `finish_guard`（造引用 + 代码围栏结构完整性）已落地、迁入 [`../03-AI核心/执行引擎架构设计.md` §四·交付前核验](/docs/03-AI核心/执行引擎架构设计.md)（→ 代码 `runtime/verify.py`）；本条收口**未落地的重层**，原草稿退役删除。

ReAct 唯一终止信号是模型自报 `done`——团队有验收结构、缺验收行为（典型事故：CEO 直答引用越界、worker 自报 done 无人回读产物）。轻层是「产出者机械自检」（纯代码、近零误报，已落地）；**重层 = 独立审查 worker**，仅对高风险交付启动（要跑 / 要重算 / 换眼睛找漏 / 回源对照），机械轻层够不着的语义/逻辑缺陷靠它兜。

> **协作生命周期定位（合·独立验证回合）**：在「拆 / 通 / 合 / 变 / 学」五环里这就是**「合」环的独立验证回合**——合环已落地的 **4a 完工判定 + 4b 语义边界对账是 CEO 可退提示词**（见 [`编排器 §收尾即验收`](/docs/03-AI核心/编排器与CEO主Agent.md)），本条重层是合环唯一「**新机制 + 每高风险回合真成本**」项。**2026-06-30 人明确暂不建**——4a 已 inline 覆盖；走「先开 §2.4 度量数据闸门、用数据证明 CEO 自检确实漏了『自己批自己』，再建」，与下方「挖坑探针缺陷率≈0」证据一致。

- **已定策略**：① 交付前核验是团队分内职责，非用户额外期望；② 责任留 CEO、动作下放团队（CEO 读短结论，不亲自当 QA）；③ 信号决定论触发——轻层宽触发、重层严触发（可运行物 / 关键数字 / 论证型成篇交付），品味走 `ask_user` 不进审查。
- **未落地硬点**：重层审查波次（`WaveScheduler` 自动追加审查尾节点）/ 分诊员（代码扫不出机械信号时廉价 LLM 判轻·重·品味）/ 核验呈现（审查节点可见、发现修正如实说、通过安静）/ 并行扇出拓扑（多 worker 并行时逐个核 vs 核拼装整体）/ `contract` 自动注入（轻层已决定论、合同规格校验仍靠 CEO `delegate` 时显式声明）。
- **价值**：高风险交付（可运行代码 / 带关键数字或法条 / 论证成篇报告）的独立复核——机械轻层结构上看不出、只有「真跑一遍 / 回源对照」才拦得住的一类。**法律垂直 GLAW 红队闸门 + 可辩护玻璃箱过程明确依赖此层**（见 §4.5 法律垂直）。
- **代价**：每次高风险交付多一轮独立 worker = 成本/延迟翻倍；触发判定与「谁修发现」（回炉原 worker vs CEO 补）的机制面。
- **就绪度 / 证据**：轻层 ✅；重层**有证据地暂缓**——2026-06 两轮「挖坑探针」（生成走真实模型、过轻层后用确定性地面真值判对错）显示**可判任务上缺陷率≈0**：算术 / 单一答案 25/25、代码必须真跑 20/20，故现在为此烧贵的重层不划算。探针已接 nightly 评测当回归绊线（`evals/cases/probe/` + `scripts/probe_code_execution.py`，软门禁 + 作业摘要）。残留风险只在「大而模糊」的语义交付（长报告埋一个错结论），那类确定性判不了、靠裁判或真实用户数据。
- **启动触发**：nightly 探针通过率抬头（缺陷率显著）/ 内测真实交付出现语义错成痛点 / 法律垂直启动需 GLAW 重层闸门。

### 4.1 人 + AI 混合群（消息页差异化形态）

消息页 IM 群聊里 `@` 唤起 agent → 接 CEO 编排，让 AI 作为群成员参与人类群聊（区别于对话页的纯 AI 团队群）。是消息页相对对话页的差异化卖点；数据层 `chat_messages.sender_type=agent` 已为此预留。

- **价值**：把 AI 团队能力带进人类社交 / 协作群——群里 `@` 某 agent 即可让它响应、查资料、执行任务，人与 AI 同会话协作。
- **代价**：要打通两套当前解耦的栈——IM（`messaging` service / `chat_messages` / firehose）↔ AI 执行引擎（CEO 编排 / `RuntimeEngine` / 事件流）。需处理：群消息识别 `@agent` → 转一次编排 run → agent 输出回写为 `chat_message`（`sender_type=agent`）→ 计费 / 限流归属 → 权限（谁能 `@`、agent 可见多少群历史）。
- **就绪度**：数据层 `sender_type=agent` 已留；IM transport（全员群 / 成员 / 实时 fan-out）与 CEO 编排引擎均已落地；**缺两栈之间的桥**（IM 消息 ↔ 编排 run）。
- **启动触发**：内测群验证人群聊价值后出现「群里直接调 AI」的明确诉求；或需把消息页做成区别于对话页的协作场景。

> **来源**：原 [`../05-平台与运维/消息IM.md`](/docs/05-平台与运维/消息IM.md) §七 P2 ⏳ 项，按文档治理迁入。

- **价值**：多 Agent 长任务里，检查点 / 发问 / 计划复核 / 队员升级散落各回合易漏；聚合成一份「待你拍板」清单（可跨回合乃至跨对话）＝老板一眼看全待办。轮次摘要卡降低长对话回溯成本。
- **代价 / 就绪度**：决策卡片体系（`CheckpointCard` / `PlanReviewCard` / `EscalationCard`）与跨对话感知（对话列表状态点 + 完成通知，[`前端UX设计 §一`](/docs/04-前端/前端UX设计.md)）已落地、聚合视图可复用其数据源；缺跨回合/跨对话聚合面板 IA 与「轮次摘要」的生成时机 / 触发规则。

### 4.5 法律垂直（首个行业垂直 · hero 已落地、库接入等 open）

> **来源**：原 `法律垂直场景设计.md`（🗂️ 已退役，2026-06「先做法律」讨论 + 同场行业调研；M1–M3 as-built 与行业调研正文见 git 历史 + 代码）。是 [产品定位 §三「行业垂直深度」壁垒](/docs/01-产品/产品定位与品牌.md) 的首个落地实例。

**为什么是法律**：法律推理**天生对抗**，恰落在 AgentCore 唯一差异点（真多 Agent 团队 + 辩论互审）上；中国法律 AI 几乎全是「单模型 + RAG」、引用可靠性公认未解（Stanford RegLab：专业 RAG 仍 17%–34% 幻觉），多 Agent 对抗核验是结构性更优解且尚无人占据。故 hero 选**「对方律师作战室」**（把立场 / 草稿扔进去 → 一队 AI 对方律师先把你打一遍、预演每条抗辩 → 你的队加固），文书类型只是产物、退居次要——只有真正独立的对抗团队做得了，单模型 incumbents 复制不了。

**已落地（M1–M3 ✅，opt-in `legal_vertical_enabled` 默认关，纯资产层不改内核）**：hero「对方律师作战室」`legal_answer_brief`（答辩状）+ 第二支「三方视角案情研判」`legal_case_analysis`（接案评估 / 诉讼策略）——`runtime/legal_skills.py` + `tests/test_legal_skills.py` + conformance 三向量（`conformance/vectors/legal.py`）进 CI；来源卡编号台账方案①（终稿已核验法条 `[n]` 连来源卡、`[待核验]` 不编角标、`finish_guard` 造引用闸门）机制现状见 [`核心接口定义.md`](/docs/02-架构/核心接口定义.md)。反幻觉四件套（检索接地 → 核验 / 红队 → 人审闸门 → 审计留痕）为「真交付律师」硬底线。
